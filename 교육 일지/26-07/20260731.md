## 핵심 개념 정리

| 개념 | 의미 |
|---|---|
| **LangSmith** | LLM/워크플로우 실행 과정을 기록·시각화·평가할 수 있는 관측(Observability) 플랫폼 |
| **Trace(추적)** | 워크플로우 한 번의 실행에서 어떤 단계를 거쳤고, 각 단계에 뭐가 들어가고 나왔는지 기록하는 것 |
| **Span** | Trace 안에서 각 개별 함수/노드 실행 단위. `@traceable`로 감싸면 하나의 Span으로 기록됨 |
| **`tracing_context(enabled=True)`** | 이 블록 안에서 실행된 코드만 LangSmith에 Trace로 전송되게 하는 컨텍스트 매니저 |
| **`@traceable`** | 함수를 LangSmith가 추적할 수 있는 단위(Run)로 등록하는 데코레이터. `run_type`으로 tool/chain 등 역할 구분 |
| **LangGraph / StateGraph** | 여러 단계(Node)를 그래프 형태로 연결해 실행 순서를 정의하는 워크플로우 프레임워크. 상태(State)를 노드 간에 주고받으며 진행 |
| **Planner → Executor → Validator** | 오늘 실습에서 쓴 3단계 패턴. 계획 수립 → 실제 작업 실행 → 결과 검증 순서로 역할을 분리 |
| **Dataset** | 워크플로우를 반복 평가하기 위해 미리 만들어둔 (입력, 기대 결과) 쌍의 모음 |
| **Evaluation** | Dataset의 여러 케이스에 대해 워크플로우를 실행하고, 결과가 기대치와 맞는지 점수로 채점하는 과정 |
| **Evaluator** | 평가 채점 기준을 코드로 정의한 함수. 단순 정답 비교뿐 아니라 "왜 그렇게 판단했는지" 근거(comment)까지 남길 수 있음 |
| **Experiment** | 하나의 Dataset에 대해 특정 버전(baseline, fixed 등)을 실행해 평가한 기록 단위. 버전 간 성능을 비교하는 데 사용 |
| **baseline vs fixed** | 수정 전/후 버전을 같은 조건으로 각각 실행·평가해 개선 효과를 정량적으로 비교하는 방식 |

## 오늘 배운 내용 요약

오늘은 **Planner → Executor → Validator** 구조로 짠 여행 일정 생성 워크플로우(LangGraph 기반)를, **LangSmith**로 추적(Trace)하고 실패를 재현·디버깅한 뒤, **Dataset 기반으로 정량 평가(Evaluation)**하는 흐름을 학습함.

```
01_setup_check         환경변수/연결 점검
02_trace_workflow      정상 실행을 LangSmith에 Trace 기록
03_trace_failure       의도적으로 실패를 재현하고 Trace로 원인 확인
04_debug_and_fix       baseline(버그 버전) vs fixed(수정 버전) 비교
05_dataset_evaluation  Dataset 생성 + baseline 정량 평가
06_compare_experiments 05번과 동일 흐름, Experiment 비교 관점 정리
workflow_components.py 위 실습 전체가 공유하는 공통 모듈
```

---

## 1. 환경 설정 점검 (`01_setup_check.py`)

- LangSmith 연동에 필요한 필수 환경변수 3종을 정의하고 누락/오설정을 사전에 검증

```python
LANGSMITH_REQUIRED = (
    "LANGSMITH_API_KEY",
    "LANGSMITH_TRACING",
    "LANGSMITH_PROJECT",
)
```

- `LANGSMITH_TRACING`은 `true/1/yes/on` 중 하나여야 하고, API Key가 플레이스홀더(`your_`로 시작)면 에러 처리
- API Key는 절대 그대로 출력하지 않고 앞 4자리·뒤 4자리만 보여주는 마스킹 처리(`masked()`) — **민감정보를 로그에 그대로 남기지 않는 습관**을 배움
- `--run` 옵션을 주면 실제로 `Client.info`를 호출해 LangSmith 서버 연결까지 확인

## 2. 정상 흐름 Trace 기록 (`02_trace_workflow.py`)

- `tracing_context(enabled=True)` 블록 안에서 워크플로우를 실행하면 해당 실행 전체가 LangSmith 대시보드에 기록됨
- `--llm` 옵션 여부로 **고정된 Plan(fixed_target)** 을 쓸지, **실제 LLM이 계획을 세우는 버전(run_workflow version="llm")** 을 쓸지 분기
- `langsmith_extra`에 `metadata`, `tags`를 실어서 실행을 태깅 → 나중에 대시보드에서 실행들을 필터링하기 쉬움

## 3. 실패 재현 & 확인 (`03_trace_failure.py`)

- 일부러 `compose` Task를 Plan에서 빠뜨린 `runtime_error` 버전을 실행해 `ValueError`를 재현
- `try/except`로 예외를 잡아 출력한 뒤, **의도한 에러가 안 나면 오히려 `RecursionError`를 던져 테스트 자체가 잘못됐음을 알리는 방어 코드**가 인상적이었음
- 이렇게 Trace를 남겨두면 LangSmith 대시보드에서 "어느 Task에서, 왜 실패했는지"를 그래프로 확인 가능

## 4. Baseline vs Fixed 비교 (`04_debug_and_fix.py`)

- 같은 입력을 **수정 전(baseline)** 과 **수정 후(fixed)** 두 버전으로 각각 실행해 결과를 비교
- `WORKFLOW_VERSION` 상수 하나만 바꿔서 어떤 버전을 실행할지 스위칭하는 구조가 간단하고 실용적
- `result["validation"]["passed"]`로 최종 PASS/FAIL 판정을 확인하고, LangSmith에 업로드된 사실까지 로그로 남김

## 5. Dataset 기반 정량 평가 (`05_dataset_evaluation.py`)

핵심 개념: **"실행 한 번 잘 됐다"가 아니라, 여러 테스트 케이스에 대해 일관되게 잘 되는지 정량적으로 평가**하는 단계.

```python
EVALUATION_CASES = [
    {"inputs": {...}, "outputs": {"expected_pass": True}},
    {"inputs": {...}, "outputs": {"expected_pass": True}},
    {"inputs": {...}, "outputs": {"expected_pass": False, "expected_failure_keyword": "예산 50,000원을 초과"}},
]
```

- `client.create_dataset()` + `client.create_examples()`로 평가 케이스를 LangSmith Dataset으로 등록 (이미 있으면 재사용, `has_dataset()`으로 체크)
- `client.evaluate(baseline_target, data=DATASET_NAME, evaluators=[workflow_evaluator], ...)`로 여러 케이스를 한 번에 돌려서 자동 채점
- **평가 기준을 코드로 명시한 부분이 핵심**:
  1. Validator의 실제 PASS/FAIL이 기대 결과와 같은가
  2. PASS 사례는 조건에 맞는 장소를 선택했는가
  3. FAIL 사례는 기대한 실패 이유를 정확히 반환했는가
  4. Task 누락 때문에 "우연히" FAIL한 건 아닌가 (거짓 FAIL 방지)

## 6. 커스텀 Evaluator 작성 (`workflow_evaluator`)

```python
def workflow_evaluator(outputs: dict, reference_outputs: dict) -> dict:
    ...
    return {
        "key": "workflow_requirement_match",
        "score": int(passed),
        "comment": f"expected_pass={expected_pass}, actual_pass={actual_pass}, ..."
    }
```

- 단순 정답/오답 비교가 아니라, **"왜 그렇게 판단했는지"까지 `comment`로 남겨서 사람이 나중에 검토할 수 있게** 설계된 점이 중요한 포인트
- `has_missing_task` 체크처럼, **"결과가 우연히 맞았을 뿐인 케이스"를 걸러내는 로직**을 따로 넣어야 한다는 걸 배움 — 단순 pass/fail 카운트보다 신뢰도 있는 평가 설계가 필요함

## 7. 공통 모듈 구조 (`workflow_components.py`)

- `Planner → Executor → Validator`를 `LangGraph`의 `StateGraph`로 구성

```python
builder = StateGraph(TraceState)
builder.add_node("planner", planner)
builder.add_node("executor", executor)
builder.add_node("validator", validator)
builder.add_edge(START, "planner")
builder.add_edge("planner", "executor")
builder.add_edge("executor", "validator")
builder.add_edge("validator", END)
```

- 각 Task 함수(`execute_requirements`, `execute_weather` 등)를 `@traceable(name=..., run_type="tool")`로 감싸서, **그래프 안의 각 노드 실행이 LangSmith에서 개별 Span으로 보이도록** 처리
- `PlanVersion`을 `Literal["baseline", "fixed", "llm", "runtime_error"]`로 제한해, 실행 버전을 오타 없이 안전하게 관리(타입 힌트 활용)

## 오늘 핵심적으로 이해한 것

1. **Trace(추적)와 Evaluation(평가)은 목적이 다르다**
   - Trace: "이번 한 번의 실행에서 무슨 일이 있었는지" 들여다보는 것 (디버깅용)
   - Evaluation: "여러 케이스에 걸쳐 일관되게 잘 동작하는지" 점수로 확인하는 것 (품질 검증용)

2. **실패를 의도적으로 재현하고 Trace로 남기는 것도 중요한 작업**이라는 점 — 정상 케이스만 보여주는 게 아니라, 실패 케이스의 원인을 명확히 추적할 수 있어야 함

3. **평가 기준(Evaluator)을 코드로 명시하면, 결과가 왜 맞았는지/틀렸는지 사람이 검토 가능** — 단순 True/False가 아니라 `comment`로 근거를 남기는 설계가 실무적으로 유용함
