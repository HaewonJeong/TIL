## 오늘 나온 핵심 개념 (한눈에 보기)

| 개념 | 한 줄 정의 |
|---|---|
| **Workflow** | 개발자가 `if`문으로 실행 순서와 Tool 사용 여부를 직접 정하는 방식 |
| **Agent** | 모델이 질문과 Tool 설명을 보고 스스로 어떤 Tool을 언제 쓸지 결정하는 방식 |
| **Tool** | 일반 Python 함수에 이름·설명·입력 Schema를 붙여 모델이 이해하고 호출할 수 있게 만든 것 |
| **Tool 계약(Contract)** | 모델에게 전달되는 Tool의 이름, 설명, 입력 JSON Schema 3요소 |
| **args_schema (Pydantic)** | Tool이 받을 입력값의 타입과 필수 여부를 미리 정의한 규격 |
| **Schema 검증 vs 업무 규칙 검증** | "타입·필수값이 맞는지"(Schema) vs "인원수가 0명이면 안 된다"처럼 함수 내부 로직으로 판단하는 것(업무 규칙) |
| **HumanMessage / AIMessage / ToolMessage** | 각각 "사용자 질문 / 모델의 생각·Tool 호출 / Tool 실행 결과"를 나타내는 메시지 타입 |
| **Action / Observation** | Agent가 Tool을 호출하는 행동(Action)과 그 결과(Observation) |
| **ReAct 패턴** | Action → Observation → (필요하면) 다음 Action 을 반복하며 스스로 전략을 수정해가는 방식 |
| **tools_condition** | 마지막 메시지에 Tool 호출이 있으면 Tool 실행으로, 없으면 종료로 보내는 LangGraph 분기 함수 |
| **Checkpointer / thread_id** | 대화를 스레드 단위로 저장해서, 같은 thread_id면 이전 대화를 기억하고 다른 thread_id면 기억하지 못하게 하는 장치 |

## 1. Workflow vs Agent (`01_workflow_vs_agent.py`)

같은 여행 질문을 **개발자가 직접 분기하는 Workflow**와 **모델이 스스로 결정하는 Agent** 두 방식으로 처리해서 비교했다.

- **Workflow**: `"장소"`, `"실내"` 같은 키워드가 있으면 `search_destination`을, `"예산"`, `"얼마"` 같은 키워드가 있으면 `estimate_day_budget`을 호출하도록 **개발자가 if문으로 미리 정해둔다.**
- **Agent**: 똑같은 Tool 2개를 모델에게 주고, 모델이 질문을 읽고 **"이번엔 어떤 Tool이 필요한지" 스스로 판단**해서 호출한다.
- 복합 질문(장소+예산을 한 번에 물어보는 경우)에서 둘의 차이가 잘 드러난다 — Workflow는 정해둔 조건에 다 걸리면 두 Tool을 순서대로 실행하고, Agent는 모델이 "둘 다 필요하다"고 판단해서 알아서 두 Tool을 호출한다.

## 2. Tool 계약 (`02_tool_contract.py`)

일반 함수와 `@tool`로 등록한 함수가 뭐가 다른지 확인했다.

- 일반 함수는 그냥 실행만 되지, 모델은 "이 함수가 뭘 하는지, 어떤 값을 넣어야 하는지" 알 방법이 없다.
- `@tool(args_schema=...)`을 붙이면 모델에게 **이름, 설명, 입력 JSON Schema**가 전달돼서, 모델이 "이 Tool은 이런 값을 넣어서 부르면 되는구나"를 이해할 수 있게 된다.
- **Schema 검증**(필수 필드 누락 같은 입력 형식 오류)은 함수가 실행되기도 전에 걸러지고, **업무 규칙 검증**(인원수가 1명 미만이면 안 됨 같은 것)은 함수 내부에서 직접 처리한다는 차이도 실습으로 확인했다.

## 3. Agent 생성 & 메시지 추적 (`03_create_agent.py`)

`create_agent()`로 실제 Agent를 만들고, 내부에서 오가는 메시지를 한 줄씩 추적해봤다.

- 대화 흐름은 `HumanMessage(질문) → AIMessage(Tool 호출 결정, tool_calls 있음) → ToolMessage(Tool 실행 결과) → AIMessage(최종 답변, tool_calls 없음)` 순서로 진행된다.
- "장소만 필요한 질문", "예산만 필요한 질문", "Tool이 필요 없는 질문", "둘 다 필요한 복합 질문" 4가지 케이스로 **Agent가 예상한 Tool을 정확히 골라 쓰는지** 검증했다.

## 4. ReAct 반복 — 실패하면 전략을 바꿔서 재시도 (`04_react_graph.py`)

앞서 만든 Agent는 "한 번 Tool 부르고 끝"이었다면, 이번엔 **Tool 결과가 부족하면 다음 Action을 스스로 바꿔서 다시 시도**하는 흐름을 만들었다.

```
START → agent(모델이 생각/Tool 호출 결정) ⇄ tools(Tool 실행) → (tools_condition으로 반복 또는 종료)
```

- 예: 처음엔 `search_mode="strict"`로 정확히 검색했는데 결과가 `NOT_FOUND`면, 모델이 힌트(`retry_hint`)를 읽고 스스로 `search_mode="broad"`로 조건을 넓혀 재검색한다.
- 반대로 예산 계산처럼 **정보(인원/입장료/식비)가 애초에 부족하면, Tool을 억지로 호출하지 않고 사용자에게 되묻는 것**도 확인했다 — Agent가 "모르면 지어내지 않고 질문한다"는 원칙을 지키는 부분.
- 이게 바로 **ReAct(Reasoning + Acting) 패턴**: 생각하고(Reasoning) → 행동하고(Acting, Tool 호출) → 결과를 보고 다시 생각하는 걸 반복하는 구조다.

## 5. Agent 기억(Memory) — Thread별로 대화 이어가기 (`05_agent_memory.py`)

Agent가 **이전 대화 내용(이름, 동행인, 예산)을 기억**해서 Tool 인자를 자동으로 채우는 실습이다.

- `InMemorySaver()`를 Agent의 `checkpointer`로 등록하면, 같은 `thread_id`로 대화할 때 **이전 메시지가 이어져서 저장**된다.
- "내 이름은 수진이고 아이와 여행해. 예산은 20만원이야" 라고 먼저 말해두면, 나중에 "내 조건에 맞는 장소를 추천해줘"라고만 물어도 Agent가 **앞에서 말한 이름·동행인·예산을 기억해서** Tool 인자로 채워 호출한다.
- 예산을 "15만원으로 변경해줘"처럼 정보를 바꾸면 **다음 Tool 호출부터는 최신 값**이 반영되고, **다른 thread_id(다른 학생)에는 이 정보가 전혀 넘어가지 않아** Agent가 대신 다시 물어본다 — 세션(사용자)별로 기억이 분리된다는 걸 보여주는 부분이다.
