## 오늘 나온 핵심 개념 (한눈에 보기)

| 개념 | 한 줄 정의 |
|---|---|
| **Chain** | 정해진 순서대로만 실행되는 고정 흐름 (LangChain, `\|` 연산자로 연결) |
| **Graph** | 분기·반복·상태 공유가 가능한 유연한 실행 흐름 (LangGraph) |
| **State** | 모든 Node가 함께 읽고 쓰는 공유 데이터 저장소 |
| **Node** | State 중 필요한 부분만 읽고, 바뀐 부분만 반환하는 처리 함수 |
| **Edge** | Node와 Node 사이의 실행 순서를 연결하는 선 |
| **Conditional Edge (Routing)** | 조건에 따라 다음에 실행할 Node를 동적으로 선택하는 분기 |
| **Reducer** | 같은 State 필드에 여러 Node가 값을 보낼 때 "덮어쓸지, 이어붙일지" 정하는 규칙 |
| **Retrieve / Generate** | RAG의 두 단계 — 관련 문서를 찾는 단계 / 그 문서를 근거로 답을 만드는 단계 |
| **Query Router** | 질문의 성격을 보고 RAG 경로로 보낼지, 그냥 LLM이 바로 답할지 나누는 분류기 |

## 오늘 배운 것 요약 (한 문장씩)

1. **Chain vs Graph**: 순서가 고정된 작업은 Chain(LangChain)만으로 충분하지만, 분기·반복·상태 공유가 필요하면 Graph(LangGraph)를 쓴다.
2. **State / Node / Edge**: Graph는 "공유 작업지(State)"를 "일꾼(Node)"들이 "순서(Edge)"대로 넘겨받아 처리하는 구조다.
3. **Reducer**: 같은 State 필드에 여러 Node가 값을 보낼 때, 덮어쓸지 이어붙일지를 정하는 규칙이다.
4. **Conditional Routing**: 질문 내용에 따라 다음에 실행할 Node를 자동으로 갈라 태우는 법을 배웠다.
5. **RAG Graph**: 검색(retrieve) → 생성(generate) 2단계를 Graph로 표현해서, 어느 단계가 문제인지 구분하기 쉽게 만들었다.
6. **Question Router**: 모든 질문에 검색(Embedding)을 다 태우지 않고, 필요한 질문만 골라서 RAG로 보내는 법을 배웠다.

## 1. Chain vs Graph (`01_chain_vs_gragh.py`)

같은 "여행지 추천" 작업을 **LangChain(`|` 연산자로 고정 순서 연결)**과 **LangGraph(Node/Edge로 순서 구성)** 두 가지 방식으로 만들어서 비교했다.

- **고정된 순서**(retrieve → generate)만 있다면 Chain으로도 충분하다.
- 분기(질문에 따라 다른 경로), 반복, 여러 Node가 State를 공유해야 하는 경우엔 Graph가 필요하다.
- 실습에서는 두 방식으로 만든 결과(`answer`)가 똑같이 나오는 걸 확인해서, "표현 방식만 다를 뿐 같은 일을 할 수 있다"는 걸 보여줬다.

---

## 2. State / Node / Edge (`02_state_node_edge.py`)

여행 예산 계산 예제로 Graph의 3요소를 확인했다.

- **State**: 모든 Node가 공유하는 데이터 묶음 (`place`, `travelers`, `ticket_price`, `total_price`, `message`, `path`)
- **Node**: State 중 필요한 필드만 읽고, 바뀐 부분만 반환하는 함수 (`calculate_total`, `make_message`)
- **Edge**: `START → calculate_total → make_message → END`처럼 실행 순서를 연결

포인트는 Node가 **State 전체를 다시 안 돌려줘도 되고, 바뀐 필드만 반환하면** LangGraph가 알아서 기존 State에 합쳐준다는 점이다.

---

## 3. State Reducer (`03_state_reducer.py`)

여러 Node가 **같은 필드(`notes`)**에 결과를 계속 추가하는 경우를 다뤘다.

- 기본적으로 State 업데이트는 "덮어쓰기"지만, `Annotated[list[str], operator.add]`처럼 **Reducer**를 지정하면 새 값을 기존 값에 **이어 붙이는 방식**으로 바뀐다.
- 관광지 조사, 예산 조사, 식사 조사, 교통 조사처럼 여러 Node가 각자 조사한 내용을 `notes`에 차곡차곡 쌓아서, 마지막에 한 번에 요약하는 흐름을 만든 실습이다.

---

## 4. Conditional Routing (`04_conditional_routing.py`)

질문 내용을 분석해서 **다음 Node를 자동으로 선택**하는 법을 배웠다.

```
classify(질문 분류) → budget / destination / general 중 하나로 분기 → END
```

- `classify` Node가 질문 속 키워드(예산 관련 단어, 장소 관련 단어)를 보고 `route` 값을 정한다.
- `add_conditional_edges()`로 "route 값에 따라 다음 Node를 다르게 연결"할 수 있다.
- "예산 질문인데 장소 검색까지 다 실행하면 낭비"라는 문제의식에서 나온 패턴 — **불필요한 작업을 건너뛰기 위한 분기**다.

---

## 5. RAG Graph (`05_rag_graph.py`)

RAG를 `retrieve`(검색) → `generate`(답변 생성) 2개의 Node로 나눠서 Graph로 만들었다.

- 문서를 Embedding해서 VectorStore에 넣고, 질문이 오면 `retrieve`가 관련 문서를 찾고, `generate`가 그 문서만 근거로 답변을 만든다.
- Graph로 단계를 나눠두면, 나중에 답이 이상할 때 **"검색이 잘못됐는지, 생성이 잘못됐는지"를 Node 단위로 구분해서 확인**할 수 있다는 게 핵심 장점이다.

---

## 6. Question Router (`06_question_router.py`)

RAG Graph에 **"이 질문이 검색이 필요한 질문인가?"를 먼저 판단하는 Router**를 추가했다.

```
classify(RAG 필요 여부 판단) → [RAG 경로: retrieve → rag_answer] 또는 [General 경로: general] → END
```

- 여행지 관련 키워드가 있으면 `retrieve → rag_answer`로, 없으면 바로 `general`(LLM이 그냥 답변)로 보낸다.
- 매번 Embedding 검색을 돌리면 비용과 시간이 드니까, **검색이 진짜 필요한 질문에만 선택적으로 검색을 태우는 것**이 이 실습의 핵심 아이디어다.

## 오늘의 핵심 정리

1. Chain은 고정된 순서, Graph는 분기·반복·상태 공유가 필요할 때 쓴다.
2. Graph는 State(공유 데이터) + Node(처리 함수) + Edge(순서/분기)로 구성된다.
3. 여러 Node가 같은 필드를 계속 채워나갈 땐 Reducer로 "덮어쓰기 vs 이어붙이기"를 정해줘야 한다.
4. Conditional Routing과 Question Router는 결국 같은 아이디어다 — **모든 요청에 같은 작업을 다 태우지 말고, 필요한 것만 골라서 실행**하자는 것.
5. RAG도 검색/생성을 Node로 나눠두면 문제가 생겼을 때 어느 단계 탓인지 더 쉽게 찾을 수 있다.
