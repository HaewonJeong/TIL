## 오늘 나온 핵심 개념 (한눈에 보기)

| 개념 | 한 줄 정의 |
|---|---|
| **Plan** | "무엇을(goal), 어떤 순서의 Task로, 무엇을 완료 기준으로 삼을지"를 담은 실행 계획 (Pydantic으로 형식 강제) |
| **Planner** | 사용자의 목표(goal)를 읽고 LLM이 구조화된 Plan을 만들어내는 역할 |
| **Task / Executor** | Plan에 담긴 각 작업(requirements, weather, destination, budget, compose)을 실제로 실행하는 조각 함수들 |
| **Context** | Executor의 각 Task가 결과를 저장하고, 다음 Task가 읽어가는 공유 저장소 |
| **Validator / ValidationReport** | 실행 결과가 원래 목표와 조건을 만족하는지 검사하고, 실패 이유를 목록으로 돌려주는 역할 |
| **Replanner / ReplanDecision** | 검증 실패 이유를 보고 "다시 시도(retry, 새 Plan 포함)할지, 포기(stop)할지" LLM이 판단하는 역할 |
| **WorkflowState** | Planner·Executor·Validator·Replanner 네 Node가 공유하는 전체 상태 |
| **ResultCode (FOUND/NOT_FOUND/TIMEOUT/AUTH_ERROR)** | 외부 검색/Tool 결과를 표준화한 상태 값 |
| **재시도 가능 vs 불가능 오류** | NOT_FOUND·TIMEOUT처럼 다시 시도해볼 만한 오류와, AUTH_ERROR처럼 재시도해도 소용없는 오류를 구분하는 것 |
| **Fallback** | 재시도 한도까지 다 써도 실패했을 때, 사용자에게 조건 변경을 요청하며 안전하게 종료하는 것 |
| **Handoff** | 자동으로 해결할 수 없는 문제(권한 오류 등)를 사람(담당자)에게 넘기는 것 |
| **Guard** | Agent/Tool의 실행 결과를 가로채서 재시도·중단 여부를 "결정적으로(코드로)" 강제하는 감시 Node |
| **recursion_limit / GraphRecursionError** | 종료 조건을 깜빡 잊은 Graph가 무한 반복에 빠지는 것을 막는 최후의 안전장치 |

## 1. 여행 도메인 모델 (`travel_domain.py`)

오늘 실습 전체가 공유하는 **데이터 규격과 순수 함수**들이 정의된 파일이다.

- `Plan`: `goal`, `tasks`(등록된 Task 이름만, 중복 금지), `success_criteria`를 담은 계획. `field_validator`로 "같은 Task 중복 등록"을 아예 차단한다.
- `TripRequest`: 날씨, 인원, 예산, 아이 동반 여부 같은 사용자 조건.
- `search_destinations`, `analyze_weather`, `calculate_budget_options`, `compose_draft`, `validate_draft`: 각각 "장소 검색", "날씨→정책 변환", "예산 계산", "일정 초안 작성", "초안 검증"을 담당하는 순수 함수들이다. 예를 들어 `compose_draft`는 예산을 만족하는 후보가 없으면 장소를 억지로 고르지 않고 `selected_place=None`으로 남겨서, Validator가 실패 원인을 명확히 판단할 수 있게 해준다.

## 2. Executor의 속 재료 (`component1.py`)

Plan에 적힌 Task 이름(`weather`, `destination`, `budget`, `compose` 등)과 **1:1로 대응하는 실행 함수들**이 정의돼 있다.

```python
def execute_destination(request, context):
    context["destinations"] = search_destinations(request)

def execute_budget(request, context):
    places = context.get("destinations", [])
    context["budget_options"] = calculate_budget_options(request, places)
```
- 각 함수는 **`context`라는 공유 저장소**에 자기 결과를 써넣고, 뒤에 오는 함수는 그 결과를 꺼내 쓴다 — 마치 이어달리기에서 바통을 넘기는 것과 비슷하다.
- `validate_execution()`은 Plan에 포함된 Task마다 "이 Task가 실제로 context에 결과를 남겼는지"부터 확인하고, `compose`가 포함돼 있으면 완성된 일정 초안(`draft`)까지 도메인 규칙(날씨/아이동반/예산)으로 검증한다.

## 3. Replanner가 쓸 부품 (`component2.py`)

Replanner 전용 데이터 모델과, LLM 준비 함수가 담겨 있다.

- `ReplanDecision`: `action`(retry 또는 stop), `reason`, 그리고 retry일 때만 필요한 새 `plan`. `model_validator`로 **"retry라고 해놓고 새 Plan을 안 주는" 모순된 응답을 막는다.**
- `WorkflowState`: goal, request, 시도 횟수(retries/max_retries), plan, context, draft, validation, action, reason까지 — Planner부터 Replanner까지 전체 여정에서 필요한 모든 필드를 한 곳에 모아둔 State.

## 4. Planner — 목표를 실행 계획으로 바꾸기 (`l_01_plan.py`)

```python
planner = ChatOpenAI(model="gpt-4o-mini").with_structured_output(Plan)
plan = planner.invoke(f"목표를 실행 task로 분해하세요...\n목표\n{goal}")
```
- LLM에게 "등록된 Task 중 꼭 필요한 것만 순서대로 고르라"고 시켜서, 자유 텍스트가 아니라 **Plan이라는 정해진 형식**으로 답을 받는다.
- 등록되지 않은 Task(`search_everything`)나 중복된 Task를 넣으면 `Plan.model_validate()`가 바로 에러를 내며 차단하는 것도 확인했다.
- 수업 노트에 있던 판단 기준이 인상적이었다: "모든 요청이 항상 destination→budget 순서라면 Workflow로 충분하고, weather/destination/budget/compose 여부가 요청마다 달라져야 Planner(LLM이 순서를 짜는 방식)가 필요하다."

## 5. 실패에 안전하게 대응하기 — Executor의 Guard 패턴 (`l_02_executor.py`)

이 파일은 "Task를 실행한다"보다는, **"실행이 실패했을 때 어떻게 안전하게 대응할까"**에 집중한 실습이다.

```
FOUND                  → 성공 종료
NOT_FOUND / TIMEOUT    → 최대 횟수 안에서 재시도
최대 횟수 도달         → Fallback 후 종료
AUTH_ERROR             → 재시도 없이 Handoff
종료 Edge가 없는 Graph → recursion_limit가 최종 차단
```

- 검색 결과를 `FOUND`/`NOT_FOUND`/`TIMEOUT`/`AUTH_ERROR` 같은 **표준 코드로 분류**하고, `route_after_search()`가 이 코드와 "지금까지 몇 번 시도했는지"를 보고 다음 Node(재시도/성공/Fallback/Handoff)를 정한다.
- 일부러 **종료 Edge가 없는 잘못된 Graph**도 만들어서, `recursion_limit`이 무한 루프를 강제로 멈추고 `GraphRecursionError`를 내는 것까지 확인했다 — "Graph를 잘못 설계해도 최소한의 안전망은 있다"는 걸 보여주는 실습.
- 마지막엔 이 Guard 로직을 **진짜 OpenAI Agent + Tool**과 결합했다. Agent가 Tool을 호출하면, `guard` Node가 그 결과를 가로채서 "재시도할지/성공 처리할지/Fallback할지/Handoff할지"를 **모델이 아니라 코드(Graph의 조건 Edge)가 결정**하게 만든 것이 핵심 포인트다 — 오늘 노트에 적힌 원칙 그대로: *"재시도 여부와 최대횟수는 모델이 아니라 Graph State와 Edge가 강제한다."*

## 6. Plan → Execute → Validate → Replan 전체 연결 (`l_03_replanner.py`)

지금까지 만든 조각(Planner, Executor, Validator, Replanner)을 **하나의 순환 Graph**로 연결했다.

```
START → planner → executor → validator ─(실패 시)→ replanner ─(retry 시)→ executor
                                 └─(성공 또는 재시도 한도 도달)→ END
```

- `validator`가 실패를 발견하면 `replanner`가 실패 이유를 보고 **"어떤 Task를 추가/수정하면 되는지"** 새 Plan을 만들어 다시 `executor`로 돌려보낸다.
- 예산 초과처럼 **Plan을 아무리 고쳐도 해결할 수 없는 실패**는 Replanner가 `stop`을 반환해서 억지로 반복하지 않고 종료한다.
- `retries >= max_retries`가 되면 검증이 실패한 상태라도 무한정 반복하지 않고 종료하도록 안전장치를 걸어뒀다.
