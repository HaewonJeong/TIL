## 1. Spring → FastAPI 호출 클라이언트

Spring이 FastAPI(`/quiz/generate`)를 호출할 수 있도록 `RestClient` 기반 클라이언트를 구현했다.

```java
@Service
public class QuizGenerationClient {

    private final RestClient restClient;

    public QuizGenerationClient(
            @Value("${agent.base-url}") String baseUrl,
            @Value("${agent.api-key}") String apiKey
    ) {
        this.restClient = RestClient.builder()
                .baseUrl(baseUrl)
                .defaultHeader("Authorization", "Bearer " + apiKey)
                .build();
    }

    public QuizGenerationResult generateQuiz(String ingredient) {
        return restClient.get()
                .uri("/quiz/generate?ingredient={ingredient}", ingredient)
                .retrieve()
                .body(QuizGenerationResult.class);
    }

    public record QuizGenerationResult(
            String statement, Boolean answer, String explanation, String confidence
    ) {}
}
```

팀에 이미 존재하던 `agent.base-url`, `agent.api-key` 설정을 그대로 재사용했고, 팀원이 만든 유사한 클라이언트(`FastApiFileClient`) 패턴을 그대로 따랐다.

## 2. 일일 퀴즈 생성 스케줄러

### 설계 원칙
점수 스케줄러(`DailyScoreScheduler`)와 완전히 독립된 별도 컴포넌트로 구현했다. 같은 자정에 실행되더라도, 서로 다른 성격의 배치 작업(회원별 반복 처리 vs 하루 1회 단발성 작업)이므로 하나로 합치지 않는 것이 예외 격리와 유지보수 측면에서 안전하다고 판단했다.

```java
@Scheduled(cron = "0 0 0 * * *")
public void generateDailyQuiz() {
    LocalDate today = LocalDate.now();

    if (quizRepository.existsByQuizDate(today)) {
        log.info("오늘의 퀴즈가 이미 존재합니다. 생성을 건너뜁니다.");
        return;
    }

    ProductNameId ingredient = pickRandomIngredient();
    QuizGenerationClient.QuizGenerationResult result = generateWithRetry(ingredient.name(), 3);

    if (result == null) {
        handleGenerationFailure(today);
        return;
    }

    Quiz quiz = Quiz.create(result.statement(), result.answer(), result.explanation(),
            ingredient.name(), ingredient.id(), today);
    quizRepository.save(quiz);
}
```

### 재료 선정 로직
서비스에 등록된 활성 상품(`is_active = true`) 중 랜덤으로 하나를 선택한다. 개인화하지 않고 전체 사용자에게 공통 퀴즈 1개만 제공하는 요구사항(QUIZ-003)에 따라, 특정 회원의 냉장고 재료가 아니라 서비스 전체 상품 테이블을 대상으로 했다.

```java
@Query("SELECT new com.naengpa...ProductNameId(p.productId, p.name) FROM Product p WHERE p.isActive = true")
List<ProductNameId> findAllActiveProductNameIds();
```

### 관리자 수동 실행 API
점수 스케줄러의 수동 실행 API(`ManualScoreController`)와 동일한 패턴으로, 완전히 별도의 `ManualQuizController`를 만들었다. 두 API를 하나로 합치자는 아이디어도 나왔으나, 예외 격리와 개별 재실행 가능성을 위해 분리를 유지하기로 결정했다. 프론트에서는 화면 공간 문제로, 버튼 하나를 클릭하면 점수/퀴즈 중 선택하는 드롭다운으로 처리해 코드 분리와 UI 간결함을 동시에 확보했다.

## 3. LLM 생성 실패 방어 로직

### 두 가지 실패 유형 구분

```java
private QuizGenerationClient.QuizGenerationResult generateWithRetry(String ingredient, int maxRetry) {
    for (int i = 0; i < maxRetry; i++) {
        try {
            QuizGenerationClient.QuizGenerationResult result = quizGenerationClient.generateQuiz(ingredient);

            if ("low".equals(result.confidence())) {
                log.warn("[품질 문제] 퀴즈 신뢰도 낮음 (시도 {}/{})", i + 1, maxRetry);
                continue;
            }
            return result;

        } catch (Exception e) {
            log.warn("[통신 문제] 퀴즈 생성 API 호출 실패 (시도 {}/{}) - {}", i + 1, maxRetry, e.getMessage());
        }
    }
    return null;
}
```

- **품질 문제**: LLM이 응답은 정상적으로 줬지만 `confidence`가 "low"인 경우
- **통신 문제**: FastAPI 호출 자체가 예외(네트워크, 타임아웃, 5xx 등)로 실패한 경우

두 유형을 하나의 재시도 횟수(최대 3회)로 통합 관리하되, 로그에서는 원인을 구분해 기록하도록 했다.

### 3회 실패 시 폴백: 과거 퀴즈 복제

```java
private void handleGenerationFailure(LocalDate today) {
    Quiz pastQuiz = quizRepository.findRandomPastQuiz()
            .orElseThrow(() -> new IllegalStateException("대체할 과거 퀴즈도 존재하지 않습니다"));
    Quiz duplicated = Quiz.createFrom(pastQuiz, today);
    quizRepository.save(duplicated);
}
```

과거 퀴즈를 랜덤으로 하나 조회할 때는 JPQL로 표현이 안 되는 `RANDOM()` 함수가 필요해, Native Query를 사용했다.

```java
@Query(value = "SELECT * FROM quizzes ORDER BY RANDOM() LIMIT 1", nativeQuery = true)
Optional<Quiz> findRandomPastQuiz();
```

`Quiz` 엔티티에는 기존 `create()`와 별개로, 과거 퀴즈를 복제하되 날짜만 오늘로 바꾸는 `createFrom()` 정적 메서드를 추가했다. 이를 통해 LLM이 완전히 실패해도 사용자에게는 항상 퀴즈가 제공되도록 보장했다.

### 단위 테스트 (Mockito)

4개 시나리오를 테스트로 작성했다.

1. 오늘 이미 퀴즈가 있으면 생성 자체를 건너뛴다 (FastAPI 호출 자체가 없어야 함)
2. 정상적으로 confidence "high"가 오면 1회 호출로 저장된다
3. confidence "low"가 왔다가 다음 시도에 "high"가 오면, 재시도 후 저장된다
4. 3회 모두 실패하면 과거 퀴즈를 복제해 저장한다

`willReturn(A).willReturn(B)` 체이닝으로 "첫 호출과 두 번째 호출에 다른 응답을 주는" 시나리오를, `willThrow(...)`로 "항상 예외가 발생하는" 시나리오를 재현했다. `verify(mock, times(n))`으로 실제 호출 횟수를, `verify(mock, never())`로 호출되지 않았음을 검증했다.

## 4. 조회 API 보완: explanation 추가

프론트 화면을 붙이는 과정에서, 이미 퀴즈를 푼 사용자가 새로고침하면 해설이 사라지는 문제를 발견했다. 원래 해설은 제출 API 응답에만 있었는데, 조회 API에는 없었기 때문이다.

```java
public record QuizTodayResponse(
        Long quizId, String statement, String sourceProductName,
        Boolean alreadySolved, Boolean submittedAnswer, Boolean isCorrect,
        String explanation
) {}
```

정답을 아직 제출하지 않은 사용자에게는 `explanation`을 `null`로 유지해 정답 유추를 방지하고, 이미 제출한 사용자에게만 해설을 함께 응답하도록 했다. 제출 API(`submit`) 응답에는 기존대로 `explanation`을 유지했는데, 제출 직후 즉시 결과를 보여주기 위해 매번 조회를 다시 하지 않아도 되도록 하기 위함이다.

## 5. 프론트 연동

퀴즈 조회/제출 화면과 관리자 대시보드에 다음을 반영했다.

- 오늘의 퀴즈 미생성 시 안내 문구, 이미 푼 경우 선택했던 답 강조 표시 및 결과 안내
- 재료명이 있으면 "🥬 {재료명}과 관련된 퀴즈예요!" 뱃지 표시
- 중복 제출(409) 시 자연스러운 안내 처리
- 관리자 대시보드에 퀴즈 스케줄러 수동 실행 버튼 추가

프론트 API 클라이언트(axios interceptor)에서 에러 객체에 HTTP status를 담아 반환하도록 수정하는 과정에, AI 코드 생성 도구가 처음에 작성한 코드에 `return` 문이 중복되어 뒤쪽 로직이 죽은 코드가 되는 문제를 발견해 직접 수정 방향을 제시했다.

## 오늘 배운 점 정리

1. **동시에 실행되는 배치라도, 성격이 다르면(반복 처리 vs 단발성 처리) 별도 컴포넌트로 분리하는 것이 예외 격리와 유지보수에 유리하다.** "같은 시간에 실행되니 합쳐도 된다"는 생각은 코드 구조상 여러 문제를 만들 수 있다.
2. JPQL로 표현할 수 없는 DB 전용 함수(`RANDOM()` 등)가 필요할 때는 `nativeQuery = true`로 순수 SQL을 그대로 실행할 수 있다.
3. LLM 실패 방어는 "품질 실패"와 "통신 실패"를 구분해서 로깅하되, 재시도 횟수는 통합 관리하는 것이 실용적이다.
4. Mockito의 `willReturn(A).willReturn(B)` 체이닝으로 "여러 번 호출될 때 순서대로 다른 값을 반환하는" 시나리오를 테스트할 수 있고, `willThrow(...)`로 예외 상황도 실제 서버 없이 재현할 수 있다.
5. API를 설계할 때, 같은 데이터(해설)라도 "언제, 누구에게 필요한지"에 따라 여러 엔드포인트에 나누어 포함시켜야 할 수 있다. 화면을 실제로 만들어보며 이런 누락을 발견하는 경우가 많았다.
6. 화면 공간 제약이 있을 때, 백엔드 코드(API)를 합치는 대신 프론트 UI(드롭다운 등)로 문제를 해결하면 코드 구조의 원칙(관심사 분리)을 지키면서도 UX 문제를 풀 수 있다.
