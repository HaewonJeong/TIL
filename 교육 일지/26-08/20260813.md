### 학습 및 수행 내용

1. **회원-점수 데이터 정합성 문제 분석**
   - 기존 OAuth2 소셜 회원가입 로직(`OAuth2AccountService`)에서 Score/ScoreHistory 생성이 애플리케이션 코드 레벨에만 존재함을 확인
   - DB 트리거 방식과 애플리케이션 코드 방식의 장단점을 비교하고, 이번엔 코드 방식을 유지하기로 결정 (트리거 방식은 JDBC 직접 삽입에도 대응 가능하지만 별도 PR로 분리)

2. **참조 무결성(FK 제약) 적용**
   - `scores`, `score_histories` 테이블에 `members` 참조 FK 제약(`ON DELETE CASCADE`)을 추가하는 Flyway 마이그레이션 작성
   - 적용 전 고아 데이터(참조 무결성 위반 데이터) 존재 여부를 사전에 SQL로 확인하는 절차의 필요성을 학습
   - 실제 적용 후 회원 삭제 테스트 중 `refresh_tokens` 테이블에서도 FK 위반이 발생함을 확인하고 원인 분석 (CASCADE 미적용 상태 발견 → 후속 이슈로 기록)

3. **Spring 트랜잭션 경계 및 self-invocation 문제 학습**
   - 스케줄러(`DailyScoreScheduler`)의 회원 단위 try-catch가 실제로는 트랜잭션 격리를 보장하지 못한다는 점을 코드 리뷰를 통해 발견
   - `@Transactional(propagation = Propagation.REQUIRES_NEW)`와 self-invocation 문제(같은 클래스 내 메서드 호출 시 프록시 미적용)의 개념을 학습

4. **N+1 쿼리 문제**
   - 스케줄러 내 `addScore()`가 만료 재료 개수만큼 반복 호출되며 Score를 중복 조회하는 N+1 패턴을 실제 코드에서 식별
   - 회원당 1회 조회, 카테고리 캐싱 등 개선 방향을 학습 (실제 적용은 후속 작업으로 보류)

5. **낙관적 락 / 비관적 락**
   - `@Version` 기반 낙관적 락과 `SELECT ... FOR UPDATE` 기반 비관적 락의 개념과 구현 방식을 Java(JPA), Node.js(Sequelize) 양쪽으로 비교 학습

6. **배치 실행 이력 관리 설계 검토**
   - `batch_execution_log` 테이블 설계(배치명, 상태, 성공/실패 카운트, 수기 실행 시 IP 기록 등)를 진행하였으나, 현재 프로젝트 규모에서의 실효성을 스스로 재검토
   - 로그(log.info) 수준으로도 현재는 충분하다고 판단하여 이번 스코프에서는 제외하기로 결정 (설계 자체는 문서화하여 보관)

7. **기타**
   - Git 브랜치 네이밍/관리, PR 템플릿 작성
   - DB 타임존(UTC) 설정과 로컬 시간(KST) 표기 차이에 대한 이해

### 느낀 점
데이터 정합성이라는 하나의 목표를 두고도 트리거 방식과 코드 방식 중 무엇을 택할지, 그리고 관찰가능성 기능(batch_execution_log)이 실제로 필요한지 스스로 판단해보는 과정이 인상 깊었다. 기능을 무조건 구현하기보다 "왜 필요한가"를 먼저 검토하고 스코프를 조정하는 것도 개발자의 중요한 판단 기준이라는 것을 체감했다.
