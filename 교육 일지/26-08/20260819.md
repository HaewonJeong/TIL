### 배경

이전에 발견한 문제(자정 스케줄러 실행 시점에 서버 재배포와 타이밍이 겹쳐, 재시도 3회가 연속 실패하던 현상)에 대해 재시도 대기시간(5초/10초/15초)을 추가하는 수정을 이미 반영해둔 상태였다. 이날은 이 수정 사항을 실제로 배포하고 검증하는 작업을 진행했다.

### 진행 내용

- FastAPI(Agent) 서버의 라우터 경로에 `/agent/v1/quiz` prefix를 추가
- Spring의 `QuizGenerationClient`가 호출하는 요청 경로(`/agent/v1/quiz/generate`)를 FastAPI 쪽 변경된 경로와 일치시킴
- 두 서버 모두 dev 브랜치에 push 후 main으로 재배포 진행

### 트러블슈팅

배포 이후 자정 스케줄러 실행 시, 퀴즈 생성 API 호출이 401 Unauthorized로 3회 연속 실패하는 새로운 문제를 발견했다.

```
로그 확인 결과:
1차 시도 - 401 Unauthorized → 5초 대기
2차 시도 - 401 Unauthorized → 10초 대기
3차 시도 - 401 Unauthorized → 15초 대기
3회 모두 실패 → 과거 퀴즈로 자동 대체 (fallback 정상 작동)
```

**중요하게 확인한 점**: 원인은 달랐지만(이번엔 배포 타이밍이 아니라 인증 오류), 이전에 설계해둔 재시도·대기시간·fallback 방어 로직이 그대로 작동해 서비스가 끊기지 않았다. 이후 관리자 수동 실행 API로 정상 동작 여부를 즉시 재검증할 수 있었다.

### 배운 점

1. 한 가지 장애 상황을 가정하고 설계한 방어 로직(재시도, 대기시간, fallback)이, 전혀 다른 원인의 장애에서도 재사용 가능하다는 것을 실제로 확인했다. 장애 대응 로직은 "특정 원인"이 아니라 "실패라는 결과" 자체를 방어하도록 설계하는 것이 효과적이라는 것을 체감했다.
2. 서버 간 API 경로(prefix)를 변경할 때는, 호출하는 쪽과 호출받는 쪽 양쪽 모두 반드시 함께 확인해야 한다는 것을 다시 확인했다.
3. Grafana 대시보드에서 재배포 시점에 지표(5xx 오류율 등) 그래프가 끊기는 현상도 함께 확인했는데, 이는 실제 장애가 아니라 재배포 중 컨테이너가 아직 기동되지 않아 Prometheus의 메트릭 수집(`/actuator/prometheus`)이 일시적으로 이루어지지 않았기 때문이라는 것을 로그로 확인했다.
