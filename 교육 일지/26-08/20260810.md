## 1. Flyway 적용 방법 정리

### Flyway가 하는 일

DB 스키마를 "버전 관리"하는 도구. `.sql` 파일을 버전 번호 순서대로 자동 실행해서, 여러 명이 같은 DB를 쓰는 팀 프로젝트에서 스키마 변경 이력을 안전하게 관리해준다.

### 기본 사용법

```
1. src/main/resources/db/migration/ 폴더에
   Vn__설명.sql 형식으로 파일 생성
   (n은 숫자, 언더바 2개, 설명은 스네이크 케이스)

2. 파일 안에 원하는 DDL(CREATE TABLE, ALTER TABLE 등) 작성

3. 백엔드 서버를 재시작(또는 최초 실행)하면
   Flyway가 "아직 실행 안 된 버전 파일들"을 감지해서
   번호 순서대로 자동 실행

4. 실행 결과는 flyway_schema_history 테이블에 자동으로 기록됨
   (버전, 설명, 실행 시각, 성공 여부 등)
```

### 실제로 만든 마이그레이션 (V13)

```sql
-- V13__create_quiz_tables.sql

CREATE TABLE quizzes (
    quiz_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    statement TEXT NOT NULL,
    answer BOOLEAN NOT NULL,
    explanation TEXT,
    source_product_name VARCHAR(50),
    source_product_id BIGINT,
    quiz_date DATE NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE quiz_results (
    quiz_result_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    member_id BIGINT NOT NULL,
    quiz_id BIGINT NOT NULL,
    submitted_answer BOOLEAN NOT NULL,
    is_correct BOOLEAN NOT NULL,
    submitted_at TIMESTAMP NOT NULL,
    UNIQUE (member_id, quiz_id),
    CONSTRAINT fk_quiz_results_member FOREIGN KEY (member_id) REFERENCES members(member_id),
    CONSTRAINT fk_quiz_results_quiz FOREIGN KEY (quiz_id) REFERENCES quizzes(quiz_id)
);
```

### 반드시 지켜야 하는 규칙

- **한 번 실행되어 팀 공용 DB(flyway_schema_history)에 기록된 파일은 절대 수정하면 안 된다.** 수정이 필요하면 새 버전 파일(예: V14)을 추가해서 `ALTER TABLE`로 반영해야 한다.
- 버전 번호가 겹치면 안 되므로, **여러 명이 동시에 작업할 때는 미리 버전 번호를 조율**해야 한다.

### 오늘 겪은 트러블슈팅

**증상**: 마이그레이션 파일을 추가하고 서버를 실행하니 아래 에러 발생

```
Detected applied migration not resolved locally: 7, 8, 9, 10, 11, 12.
```

**원인**: 공용 DB(RDS)에는 이미 다른 팀원들이 실행한 V7~V12까지의 이력이 남아있는데, 로컬 `db/migration` 폴더에는 그 파일들이 아직 없는 상태였다. 팀원들이 로컬에서는 마이그레이션을 실행했지만, 해당 PR이 아직 `dev` 브랜치에 머지되지 않아 로컬 git 저장소에는 반영되지 않았던 것.

**해결 과정**:
```
1. dev 브랜치를 pull 받아서 누락된 버전 파일들을 최대한 확보
2. 그래도 특정 버전(V12)이 없어 계속 에러 → 팀 채널에 공유해서 확인
3. 해당 팀원 PR이 머지되기를 기다린 뒤 다시 pull
4. 로컬 폴더에 V1~V13까지 모두 채워진 뒤 서버 재실행 → 정상 적용
```

**배운 점**: Flyway 버전 관리는 "로컬 파일"과 "DB에 실제 적용된 이력"이 항상 동기화되어야 하며, 팀 작업 시에는 버전 번호 선점과 PR 머지 타이밍을 팀원과 계속 소통해야 한다는 것을 체감했다.

## 2. 테이블 설계 시 논의했던 것들

### 테이블명: 단수형 → 복수형으로 변경

팀 기존 테이블들(`products`, `recipes`, `score_histories` 등)이 전부 복수형 네이밍을 쓰고 있는 것을 확인하고, `quiz` → `quizzes`, `quiz_result` → `quiz_results`로 통일했다.

### FK 제약 여부

같은 성격의 "이력 테이블"인 `score_histories`는 FK가 없는 반면, 다른 도메인(`llm_usage_logs`)은 FK가 있는 것을 확인했다. 팀 내에서도 통일된 규칙이 없다는 것을 확인한 뒤, 아래 이유로 `quiz_results`에는 FK를 걸기로 직접 판단했다.

```
- 테스트 환경에서 회원이 물리적으로 삭제되는 경우가 실제로 있음
- 관리자 통계(정답률 등) 조회 시, 삭제된 회원의 데이터가 섞여 
  집계가 왜곡될 수 있음
```

### created_at / submitted_at 컬럼

DB의 `DEFAULT now()` 대신, 팀 기존 패턴(`ScoreHistory`)과 동일하게 JPA의 `@PrePersist`로 애플리케이션 레벨에서 값을 채우도록 통일했다.

## 3. 오늘의 퀴즈 조회 API

### 설계 포인트

- `answer`(정답)는 응답에 포함하지 않는다 (풀기 전에 정답을 알면 안 되므로).
- 오늘의 퀴즈가 아직 생성되지 않은 경우, 에러가 아니라 200 응답 + 안내 상태로 처리한다.
- 이미 푼 사용자에게는 "이미 풀었다"는 사실뿐 아니라, **그때 선택했던 답과 정답 여부**까지 함께 내려준다. (프론트에서 선택했던 보기를 강조 표시하고 나머지는 회색으로 처리하는 화면을 만들기 위함)

```java
Optional<QuizResult> resultOpt = quizResultRepository.findByMemberIdAndQuizId(member.getId(), quiz.getQuizId());

if (resultOpt.isPresent()) {
    QuizResult result = resultOpt.get();
    return new QuizTodayResponse(
            quiz.getQuizId(), quiz.getStatement(), quiz.getSourceProductName(),
            true, result.getSubmittedAnswer(), result.getIsCorrect()
    );
}
```

처음에는 "이미 풀었는지 여부(boolean)"만 확인하는 `existsBy...` 메서드를 썼는데, 화면 요구사항(선택했던 답 강조 표시)을 다시 확인하면서 `findBy...`로 바꿔 전체 데이터를 가져오도록 수정했다.

## 4. 오늘의 퀴즈 제출 API

### 설계 포인트

- 제출 시점에 실제 정답(`quiz.getAnswer()`)과 제출한 답을 비교해서 정답 여부를 판정한다.
- 정답이면 기존에 만들어둔 `ScoreService.addScore()`를 재사용해서 점수를 반영한다. (새로운 점수 반영 로직을 만들지 않고 기존 코드 재사용)
- 중복 제출은 `quiz_results`의 UNIQUE 제약과, 서비스 레이어의 사전 체크로 이중 방어한다.
- 팀의 예외 처리 컨벤션(`~AlreadyAnsweredException`처럼 의미가 담긴 커스텀 예외 클래스 + `GlobalExceptionHandler`에서 409로 매핑)을 그대로 따라, `QuizAlreadySolvedException`을 새로 정의했다.

```java
boolean isCorrect = request.submittedAnswer().equals(quiz.getAnswer());

quizResultRepository.save(
        QuizResult.create(member.getId(), quiz.getQuizId(), request.submittedAnswer(), isCorrect)
);

if (isCorrect) {
    scoreService.addScore(member.getId(), ScoreReason.QUIZ_CORRECT, null, null, 2);
}
```

`ScoreReason` enum에 `QUIZ_CORRECT`를 추가했는데, 이미 만들어둔 사유별 점수 집계 쿼리(`GROUP BY sh.scoreReason`)가 이 새 사유도 코드 수정 없이 자동으로 잡아낸다는 것을 확인했다. (Enum 값만 추가하면 기존 통계 API에 자동 반영되는 구조로 설계되어 있었음)

## 5. GET vs POST에 대한 이해 정리

작업하면서 헷갈렸던 개념을 정리했다.

- GET(조회) API도 내부적으로 여러 테이블을 조회하고 조합하는 로직을 가질 수 있다. "조회"라는 것이 "로직이 없다"는 뜻이 아니라 "데이터를 변경하지 않는다"는 뜻이다.
- API 설계 단위는 "테이블 개수"가 아니라 "화면(기능)이 필요로 하는 단위"로 정한다. 프론트가 여러 API를 호출해서 직접 데이터를 조합하게 하는 것보다, 백엔드가 필요한 데이터를 미리 조합해서 하나의 응답으로 내려주는 것이 더 좋은 설계라는 것을 다시 확인했다.

## 6. FastAPI 연동 준비 (quiz00)

퀴즈 생성을 위한 LLM 호출은 팀원이 이미 구축해둔 FastAPI 서버(`NaengpaMaster Agent`)에 라우터를 추가하는 방식으로 진행하기로 했다.

```python
router = APIRouter(prefix="/quiz", tags=["quiz"])
client = OpenAI()

@router.get("/generate")
def generate_quiz(ingredient: str):
    prompt = f"""
    "{ingredient}"의 보관, 소비, 신선도 유지와 관련된 O/X 퀴즈를 하나 만들어줘.
    ...
    """
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}]
    )
    return json.loads(response.choices[0].message.content)
```

공용 서버에 라우터를 추가하는 작업이라, 팀원 확인을 먼저 받기로 하고 오늘은 코드만 준비해두었다.

## 오늘 배운 점 정리

1. **Flyway는 "로컬 파일"과 "DB에 실제 적용된 버전"이 항상 일치해야 하며, 팀 작업 시 버전 번호 선점/PR 머지 타이밍 소통이 중요하다.**
2. 팀 컨벤션(테이블 복수형 네이밍, FK 여부, 예외 클래스 패턴)은 코드 몇 군데만 봐도 파악할 수 있고, 새 기능을 만들 때 이를 확인하고 따르는 습관이 코드 일관성에 중요하다.
3. 화면 요구사항이 구체화되면(예: "이미 선택한 답을 강조 표시"), API 응답 설계도 그에 맞춰 다시 점검해야 한다 — 처음엔 boolean 하나면 충분하다고 생각했지만, 실제 화면 요구사항을 확인하며 필드를 추가했다.
4. Enum 값을 하나 추가하는 것만으로 기존 통계 쿼리(GROUP BY)에 자동으로 반영되는 구조를 미리 설계해두면, 나중에 기능이 확장돼도 기존 코드를 수정할 필요가 없다.
