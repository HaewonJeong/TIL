## 1. 사유별 점수 획득 현황 API

### 목적
점수 변동 사유(레시피 등록, 만료 방어 성공, 만료 방치 등)별로 **발생 횟수**와 **합계 점수**를 집계해서 보여준다.

### 핵심 구현

JPQL의 `new` 생성자 표현식을 사용해, 쿼리 결과를 바로 DTO로 매핑했다. (기존 통계 도메인 코드의 패턴을 그대로 따름)

```java
@Query("""
        SELECT new com.naengpa...ScoreByReasonResponse(
                    CAST(sh.scoreReason AS string), COUNT(sh), SUM(sh.scoreDelta)
        )
        FROM ScoreHistory sh
        WHERE sh.memberId = :memberId
        AND sh.createdAt >= :startOfMonth
        GROUP BY sh.scoreReason
        """)
List<ScoreByReasonResponse> findScoreSummaryByReason(
        @Param("memberId") Long memberId,
        @Param("startOfMonth") LocalDateTime startOfMonth);
```

### 트러블슈팅 / 배운 것

- **JPQL 생성자 표현식에서 Enum → String 변환**: `ScoreReason`은 Enum 타입이라 DTO의 `String` 필드에 바로 매핑되지 않는다. `CAST(sh.scoreReason AS string)`으로 명시적 형변환이 필요했다.
- **집계 함수의 반환 타입 규칙**: `COUNT()`, `SUM()`은 원본 필드가 `Integer`여도 항상 `Long`을 반환한다. DTO 필드를 원시타입(`long`, `int`)이 아니라 래퍼타입(`Long`)으로 맞춰야 JPQL 생성자 매칭이 성공한다. 처음엔 타입 불일치로 컴파일 에러를 겪었다.

## 2. 이번 달 점수 변동 요약 API

### 목적
이번 달 1일부터 오늘까지의 **총 획득 점수**, **총 감점**, **순변동**을 계산해서 보여준다.

### 핵심 구현

```java
@Query("""
        SELECT new com.naengpa...ScoreSummaryResponse(
                    SUM(CASE WHEN sh.scoreDelta > 0 THEN sh.scoreDelta ELSE 0 END),
                    SUM(CASE WHEN sh.scoreDelta < 0 THEN sh.scoreDelta ELSE 0 END),
                    SUM(sh.scoreDelta)
        )
        FROM ScoreHistory sh
        WHERE sh.memberId = :memberId
        AND sh.createdAt >= :startOfMonth
        """)
ScoreSummaryResponse findMonthlySummary(
        @Param("memberId") Long memberId,
        @Param("startOfMonth") LocalDateTime startOfMonth);
```

`CASE WHEN`을 이용해 양수(획득)/음수(감점)를 구분해서 각각 합산했다.

### 설계 결정 — 조회 기간

- 기존 팀 기능들(만료 통계: 최근 7일, 관리자 대시보드: 최근 7일/30일/전체 선택)과 기간 방식이 다르지만, "점수 분석"은 월 단위 리포트 성격(카드 명세서와 유사)이 자연스럽다고 판단해 **이번 달(1일~오늘) 기준**으로 확정했다.
- 같은 프로젝트 안에서도 기능 목적에 따라 조회 기간 방식이 다른 것은 자연스러운 설계라는 결론에 도달했다. (실제로 팀 내 다른 도메인들도 서로 다른 기간 정책을 쓰고 있음을 확인함)
- **사유별 현황 API에도 동일하게 "이번 달" 필터를 추가**했다. 이유: 최대 영향 사유 API가 사유별 현황 API의 결과를 그대로 재사용할 예정인데, 사유별 현황이 전체 기간이면 "이번 달 최대 영향 사유"라는 이름과 실제 내용이 맞지 않게 되는 논리적 모순을 사전에 발견해 수정했다.

### API URL 설계

- 처음엔 `/analysis/monthly-summary`로 설계했으나, "이번 달"이라는 집계 기준이 향후 바뀔 가능성(예: 최근 30일로 변경)을 고려해 `/analysis/summary`로 URL을 일반화했다. 구현 로직과 API 계약(URL)을 분리해, 집계 기준만 바뀌어도 URL을 유지할 수 있도록 설계했다.

## 3. 이번 달 최대 영향 사유 API

### 목적
이번 달 점수 변동 중 **절댓값 기준**으로 가장 큰 영향을 준 사유 하나를 조회한다.

### 핵심 구현

새 쿼리를 만들지 않고, 사유별 현황 API의 조회 결과를 서비스 레이어에서 재사용했다.

```java
List<ScoreByReasonResponse> byReason = getScoreByReason(email);

return byReason.stream()
        .max(Comparator.comparingLong(r -> Math.abs(r.totalDelta())))
        .orElse(null);
```

- **왜 발생 횟수가 아니라 합계 점수(totalDelta)의 절댓값 기준인지**: "얼마나 자주 발생했는가"보다 "내 점수에 얼마나 큰 영향을 줬는가"가 하이라이트의 목적에 더 부합한다고 판단했다.
- **데이터가 없을 때(신규 가입 등)** `data: null`로 응답하도록 설계했고, 이를 API 명세서에 명시했다. 예외로 처리하지 않고 정상 응답(200)으로 처리한 이유는, 신규 가입 회원에게 하이라이트가 없는 것은 에러 상황이 아니라 정상적인 빈 상태이기 때문이다.

## 4. 프론트 연동

- 점수 상세 화면의 "점수 분석" 탭에 세 API를 연동했다.
- 사유별 현황은 **발산형 가로 막대그래프**(0을 기준으로 왼쪽은 차감/빨강, 오른쪽은 획득/초록)로 시각화했다. 처음엔 도넛 차트를 고려했으나, 감점(음수)과 획득(양수)이 함께 있는 데이터 특성상 발산형 막대그래프가 더 직관적이라고 판단해 변경했다.
- 조회 기간(예: 2026.08.01 ~ 2026.08.07)은 API 응답에 포함시키지 않고, 프론트에서 클라이언트 시간 기준으로 계산해 표시하도록 역할을 분리했다.

## 오늘 배운 점 정리

1. JPQL의 `new` 생성자 표현식을 사용할 때는 **DTO 필드 타입을 집계 함수의 실제 반환 타입(Long)과 정확히 맞춰야 한다.**
2. Enum 타입 필드를 문자열로 받으려면 **`CAST(... AS string)`으로 명시적 형변환**이 필요하다.
3. 하나의 프로젝트 안에서도 **각 기능의 목적에 맞게 조회 기간 정책을 다르게 설계**하는 것이 자연스러우며, 그 이유를 설명할 수 있으면 오히려 설계 근거가 된다.
4. API를 여러 개로 나눌 때, 한 API의 결과를 다른 API가 재사용하는 구조라면 **두 API의 "이름이 암시하는 의미"가 서로 어긋나지 않는지** 먼저 점검해야 한다.
5. **백엔드는 화면이 필요로 하는 형태로 이미 가공된 데이터를 내려주고, 프론트는 받은 데이터를 그대로 표시만 하는 것**이 좋은 API 설계라는 것을 이번 작업을 통해 체감했다. (원본 데이터를 그대로 던지고 프론트에서 계산하게 하는 방식보다 안전하고 유지보수가 쉽다.)
