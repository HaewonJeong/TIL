### 진행 내용

2차 프로젝트 발표(6분, 이후 개인 담당 파트 5분 30초로 조정) 슬라이드와 스크립트를 준비했다.

- 담당 파트(점수 정책·분석, AI 오늘의 퀴즈·스케줄러, 외부 API 장애 대응) 슬라이드 구성 정리
- 슬라이드 흐름을 점수 정책 → 점수 분석(JPQL) → AI 퀴즈 생성 → Spring-FastAPI 구조 분리 → 트러블슈팅 순서로 구성
- JPQL을 사용한 이유(엔티티 기준 집계, new 생성자 표현식으로 DTO 직접 매핑)를 발표 언어로 정리
- AI 오늘의 퀴즈 흐름(스케줄러 → 재료 선택 → LLM 호출 → confidence 검증 → 저장 → 조회)을 발표용으로 요약
- 어제 겪은 트러블슈팅(재배포 타이밍 문제로 설계한 방어 로직이, 이후 인증 오류 장애에서도 동일하게 작동한 사례)을 발표 스토리로 재구성
- 전체 스크립트 시간을 측정하며 분량 조정

### 배운 점

1. 발표 자료를 만들 때, 실제로 겪은 순서와 발표에서 말하는 순서가 다를 수 있다는 것을 확인했다. 이번 트러블슈팅의 경우, 처음 원인(배포 타이밍)과 나중에 검증된 사례(인증 오류)가 서로 다른 사건이었는데, 이를 하나의 흐름으로 정리하려다 스크립트와 스크린샷이 서로 맞지 않는 문제를 겪었다. 발표 자료를 만들 때는 각 슬라이드의 근거 자료(로그, 스크린샷)가 실제로 그 문장이 설명하는 사건과 일치하는지 다시 확인하는 과정이 필요하다는 것을 배웠다.
2. 기술적으로 사소해 보이는 부분(예: "제출 즉시 점수 반영")과, 실제로 강조할 가치가 있는 설계(예: 트랜잭션 처리, 날짜 검증)를 구분하는 연습을 했다. 모든 코드를 다 설명하려 하기보다, 어떤 선택에 "이유"가 있는지를 중심으로 발표 내용을 추려야 한다는 것을 확인했다.
3. 정해진 발표 시간에 맞추기 위해, 배경 설명보다 핵심 설계와 근거를 우선하는 방식으로 스크립트를 다듬었다.
