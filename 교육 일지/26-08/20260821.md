## 1. 발표 스크립트 완성

2차 프로젝트 발표(개인 담당 파트 5분 30초) 슬라이드 구성과 스크립트를 최종 정리했다.

```
구성: 점수 정책 개요 → 점수 분석(JPQL) → AI 오늘의 퀴즈 →
      Spring-FastAPI 구조 분리 → 트러블슈팅(재배포 타이밍)
```

- JPQL을 선택한 이유, LLM confidence 검증, 하루 1회 생성으로 비용 절감한 이유 등 각 설계 결정의 "왜"를 스크립트에 명확히 담았다.
- 트러블슈팅 슬라이드는 실제 겪은 사건 순서(첫 발견 → 원인 조사 → 해결책 설계 → 이후 다른 장애에서도 검증됨)에 맞춰 스토리를 재구성했다.
- 표현을 다듬는 연습도 했다 (예: "서비스가 안정적으로 돌아가게 했다" → "서비스 연속성을 확보했다").

## 2. 모의 면접 피드백 반영

모의 면접에서 "전공자로서 개발 직무 경험이 부족해 보인다"는 피드백을 받아, 이를 보완할 수 있는 실제 개발 에피소드를 정리했다.

정리한 에피소드 예시:
- 스케줄러 재배포 타이밍 트러블슈팅 (로그 기반 원인 추적)
- LLM 응답 신뢰성 방어 설계 (confidence 검증 + 재시도 + fallback)
- JPQL 집계 쿼리 설계 (SQL 대신 JPQL을 선택한 이유)
- Spring-FastAPI 역할 분리 아키텍처 결정
- 제출 API 날짜 검증 로직 (엣지 케이스 발견 및 방어)

예상 질문과 꼬리 질문에 대한 답변도 함께 준비했다. 특히 "완벽하다"고 주장하기보다 "한계를 알고 있지만 이런 이유로 이렇게 판단했다"는 톤으로 답변하는 연습을 했다.

## 3. 실무 개념 학습

- **DAU/MAU**: 일간/월간 활성 사용자 수 개념과, `COUNT(DISTINCT member_id)` 기반 집계 쿼리 설계 방법을 학습했다.
- **Stickiness(DAU/MAU 비율)**: 서비스가 얼마나 습관적으로 사용되는지를 보여주는 지표라는 것을 확인했다.
- 이 개념을 본인이 만든 점수 분석 기능(JPQL GROUP BY 집계)과 연결지어 설명하는 연습을 했다.
