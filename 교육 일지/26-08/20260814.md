## 1. 코드 구조 리팩토링 (팀 컨벤션 정렬)

기존에 하나의 파일에 몰려 있던 퀴즈 생성 로직을, 팀원의 `receipt_analysis_service.py` / `ingredient_vision_prompt.py` 패턴을 참고해 역할별로 분리했다.

```
app/api/quiz.py                        → 라우팅만 담당
app/services/quiz_generation_service.py → OpenAI 호출, 응답 파싱 담당
app/services/quiz_generation_prompt.py  → 프롬프트 텍스트만 담당
```

이 과정에서 팀원 코드의 `client.responses.create()` 방식과 딸이 쓰던 `client.chat.completions.create()` 방식이 다르다는 걸 확인했으나, 이미 검증된 방식을 유지하는 게 더 안전하다고 판단해 API 호출 방식 자체는 바꾸지 않고 "구조(파일 분리)"만 맞췄다.

## 2. 프롬프트 및 응답 안정성 개선

### 코드블록 방어
LLM이 순수 JSON 대신 마크다운 코드블록(` ```json `)으로 감싸서 응답할 경우를 대비해, 파싱 전에 코드블록을 제거하는 함수를 추가했다.

```python
def _strip_code_block(text: str) -> str:
    text = text.strip()
    if text.startswith("```"):
        text = text.removeprefix("```json").removeprefix("```").strip()
        text = text.removesuffix("```").strip()
    return text
```

### JSON 형식 강제
OpenAI API의 `response_format={"type": "json_object"}` 옵션을 추가해, 모델이 JSON 형식이 아닌 응답을 만들 가능성을 원천적으로 줄였다.

### 프롬프트 문구 보완
"보관, 소비, 신선도 유지" 범위는 유지하면서, "사람들이 의외로 많이 틀리는 재미있는 상식"이라는 표현을 추가해 문제의 흥미도를 높이되 원래 요구사항(QUIZ-001) 범위를 벗어나지 않도록 조정했다.

## 3. LLM 사용량 로그 연동

팀원이 이미 구축해 둔 `llm_usage_logs` 공용 테이블과 `LlmUsageLogService`에, 퀴즈 생성 기능도 기록을 남기도록 연동했다.

### 주요 설계 결정

**member_id를 nullable로 변경**
자동 스케줄러(자정 실행)는 특정 로그인 사용자가 없는 시스템 작업이라, 기존 `member_id NOT NULL` 제약과 충돌했다. 가짜 "시스템 회원"을 만드는 대신, `member_id`를 nullable로 바꾸고 자동 실행 시 null로 기록하는 방식을 택했다. 실제 데이터가 아닌 것을 데이터처럼 꾸며내는 것보다, "값이 없다"는 사실을 그대로 표현하는 게 데이터 모델링 관점에서 더 정직하다고 판단했다.

**자동/수동 실행 구분**
```java
@Scheduled(cron = "0 0 0 * * *")
public void generateDailyQuiz() {
    generateQuizInternal(null);  // 자동: memberId 없음
}

public void generateDailyQuizManually(Long memberId) {
    generateQuizInternal(memberId);  // 수동: 관리자 memberId
}
```
관리자가 스케줄러를 수동 실행하면 실제 로그인한 관리자의 `memberId`가, 자정에 자동 실행되면 `null`이 기록되도록 진입점을 분리했다.

**비용 계산 책임을 한 곳으로**
FastAPI에서도 비용을 계산하는 방안을 검토했으나, 이미 Java(`LlmUsageLogService`)에 동일한 단가표와 계산 로직이 있다는 걸 확인하고 중복 구현을 피했다. FastAPI는 토큰 사용량만 정직하게 보고하고, 비용 계산은 Java 쪽 단일 책임으로 유지했다.

## 4. 트러블슈팅

### (1) 필드명 오타로 인한 값 누락
```python
"comletionTokens": response.usage.completion_tokens,  # completion 오타
```
Python 딕셔너리 키 오타로, Java의 `UsageInfo` 레코드가 해당 필드를 찾지 못해 `null`로 채워지고, DB의 NOT NULL 제약에 걸려 저장이 실패했다. 오타를 수정해 해결했다.

### (2) DB CHECK 제약 누락
```
ERROR: new row for relation "llm_usage_logs" violates check constraint "chk_llm_usage_logs_feature_type"
```
Java Enum(`LlmFeatureType`)에 `QUIZ_GENERATION`을 추가했지만, DB에 별도로 걸려 있던 CHECK 제약의 허용 목록에는 반영되지 않아 저장이 거부됐다. 마이그레이션으로 제약을 재정의해 해결했다. Enum에 값을 추가하는 것과 DB 제약을 갱신하는 것은 별개의 작업이라는 것을 다시 확인했다.

### (3) 모델명 불일치로 비용 계산 누락
```
modelName: "gpt-4.1-mini-2025-04-14"  (실제 응답에 찍힌 값)
```
FastAPI가 OpenAI 응답의 `response.model`(구체적인 스냅샷 버전명)을 그대로 전달했는데, Java의 비용 계산 로직은 `"gpt-4.1-mini"`와 정확히 일치하는 문자열만 인식하도록 되어 있어 비용이 0으로 계산됐다. 요청 시 사용한 모델명(`MODEL` 변수)을 응답에 그대로 사용하도록 수정해 해결했다.

### (4) Flyway checksum 불일치 (2회 반복)
같은 버전 번호의 마이그레이션 파일을 실행 후 삭제했다가, 이후 다시 같은 번호로 새 파일을 만들면서 DB에 기록된 checksum과 로컬 파일의 checksum이 달라 검증에 실패하는 문제를 두 차례 겪었다.
```
Migration checksum mismatch for migration version 26/27
-> Applied to database : 0
-> Resolved locally    : (실제 값)
```
`flyway_schema_history`에서 해당 버전 기록을 삭제한 뒤 재실행하는 방식으로 해결했다. 이 작업은 팀 공용 RDS를 직접 수정하는 것이므로, 진행 전 팀원에게 상황을 공유하고 동의를 구한 뒤 진행했다.

## 오늘 배운 점 정리

1. Enum에 값을 추가하는 작업은, 코드(Java Enum)뿐 아니라 DB에 별도로 걸린 CHECK 제약까지 함께 갱신해야 완전히 반영된다.
2. 외부 API가 돌려주는 값(모델명 등)은 요청 시 지정한 값과 다르게 나올 수 있으므로, 이후 로직에서 정확한 문자열 비교가 필요한 경우 응답값을 그대로 신뢰하기보다 원래 지정한 값을 사용하는 것이 안전하다.
3. 같은 성격의 계산 로직(비용 계산 등)을 여러 서비스에 중복 구현하지 않고, 한 곳에만 두고 나머지는 필요한 원본 데이터(토큰 수 등)만 전달하는 것이 유지보수에 유리하다.
4. Flyway 마이그레이션 파일은 한 번 실행된 버전 번호를 재사용하면 checksum 불일치가 발생하며, 이는 로컬 개발 중 파일을 삭제·재생성하는 습관에서 비롯될 수 있다. 문제가 생기면 이력 삭제 전에 팀 공용 DB에 영향이 있는지 반드시 확인해야 한다.
5. 실제 데이터가 없는 상황(시스템 자동 작업 등)을 억지로 채우기보다, nullable 컬럼으로 "값이 없다"는 사실을 정직하게 표현하는 것이 더 나은 데이터 모델링이다.
