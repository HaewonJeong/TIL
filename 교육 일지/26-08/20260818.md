## 1. 발견한 문제

`score_histories` 테이블에서, 8/18 00:00과 00:56에 완전히 동일한 내용(같은 상품, 같은 순서)이 두 번 저장된 것을 확인했다.

```
125~131번 row (00:00 생성)
132~138번 row (00:56 생성) → 125~131과 완전히 동일한 데이터
```

같은 날 퀴즈도 00:00엔 "이미 존재함"으로 스킵됐는데, 실제 퀴즈는 00:56에 생성되어 있었고, 그날 LLM 사용량 로그는 아예 남지 않았다.

---

## 2. 조사 과정

### AWS 콘솔 로그 직접 확인
- Elastic Beanstalk → Logs → CloudWatch Logs 경로로 접근하는 방법을 익혔다.
- 로그 그룹: `/aws/elasticbeanstalk/{환경명}/var/log/eb-docker/containers/eb-current-app/stdouterr.log`
- 이 안에서 실제 애플리케이션 로그(`DailyQuizScheduler`, `DailyScoreScheduler`의 `log.info` 메시지)를 시간대별로 검색해 확인했다.

### 확인된 사실
```
- 인스턴스는 1대(단일 인스턴스 환경)로 확인 → "여러 대가 동시 실행" 가설은 배제
- 자정 즈음 실제 재배포(app-deploy)가 있었음을 eb-engine.log에서 확인
- 8/18 배포부터 컨테이너 실행 명령에 -Duser.timezone 옵션이 추가된 것을 확인
- 팀원 확인 결과, 그 시각에 직접 push한 사람은 없다고 함 (원인 미확정)
```

## 3. 현재까지 결론

- 데이터가 중복 저장되고 점수가 이중 차감된 사실은 DB 조회로 명확히 확인했다.
- 재배포 타이밍과 스케줄러 실행이 겹쳤을 가능성이 높지만, 정확히 "무엇이 배포를 트리거했는지"는 CI/CD 설정을 아는 담당자 확인이 필요한 영역이라 오늘은 결론을 내리지 못했다.
- 확인된 사실만 팀 채널에 공유하고, 내일 같은 현상이 재현되는지 관찰한 뒤 다시 확인하기로 했다.

## 4. 오늘 배운 점

1. AWS CloudWatch Logs에서 Elastic Beanstalk 애플리케이션 로그를 직접 찾아 특정 시간대 이벤트를 검색하는 방법을 익혔다. (로그 그룹 → 로그 스트림 → 시간 필터 + 검색어)
2. 스케줄러 이상 현상은 애플리케이션 로그만으로는 부족할 때가 있고, 인프라 로그(docker, nginx, eb-engine)를 함께 봐야 재배포 등 외부 요인과의 상관관계를 확인할 수 있다.
3. 원인을 100% 확정하지 못했더라도, 확인된 사실(데이터 중복, 재배포 발생 시각)만으로도 팀에 공유할 가치가 있다는 것을 실무적으로 체감했다. 원인 규명은 혼자 끝까지 파기보다 관련자와 나눠서 진행하는 것이 효율적이다.

## 5. QA 진행 (홈/점수/통계/퀴즈 15건)

홈 화면, 나의 냉파(점수), 점수 분석, 회원 통계, 퀴즈 영역에 대해 정상/예외 케이스 15건을 테스트했다.

```
정상 케이스(홈 진입, 점수 조회, 분석 3종, 통계, 퀴즈 조회/제출/오답/연타 방지 등): 13건 PASS
```

### 발견 및 확인한 예외 케이스 2건

**케이스 1: 홈 데이터 일부 API 실패**
- 냉장고 API(`GET /api/v1/fridge-items?fridgeId=5`)만 네트워크 차단 후 홈 진입
- 결과: 나머지 카드(장보기, 레시피, 점수)는 정상 표시되고, 실패한 영역만 빈 상태로 처리됨 → 의도대로 PASS

**케이스 2: 퀴즈 조회 API 자체 실패**
- `GET /api/v1/quizzes/today` 네트워크 요청을 강제로 차단한 뒤 퀴즈 탭 진입
- 결과: 흰 화면이나 무한 로딩 없이 "Network Error" 안내 문구가 정상적으로 표시됨 → 예외 처리 확인되어 PASS

두 케이스 모두 처음엔 재현 방법이 명확하지 않아 "판정 불가"로 남아 있었으나, 브라우저 개발자 도구의 Network 탭에서 특정 API 요청을 차단(Block request URL)하는 방식으로 재현해 확인했다.
