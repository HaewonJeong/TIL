## 2. 빌드 산출물 — WAR vs JAR

Spring 프로젝트를 빌드하면 나오는 두 가지 결과물의 차이를 배웠다.

- **WAR**: 내장 톰캣이 **없는** 형태. 그래서 Tomcat 같은 외부 WAS(Web Application Server)에 직접 배포해줘야 실행된다.
- **JAR(Spring Boot의 실행 가능한 jar)**: 내장 톰캣이 **포함된** 형태. 그래서 별도 서버 설치 없이 `java -jar 파일명.jar` 명령 하나로 바로 실행할 수 있다.
- 이 차이가 중요한 이유는, Docker로 배포할 때도 "내장 톰캣이 있는 JAR이면 컨테이너 안에서 바로 실행 가능"하기 때문이다 — 그래서 오늘 Docker 실습도 JAR을 만드는 것부터 시작했다.

## 3. Docker로 Spring Boot 앱 배포하기

### Dockerfile 추가 & 이미지 빌드
```bash
docker build -t wony77/dockertest .
```
- 프로젝트에 Dockerfile을 추가한 뒤, 위 명령으로 이미지를 빌드한다. `-t`는 이미지 이름(태그)을 지정하는 옵션이다.
- 만약 빌드가 안 되면, **Gradle → Tasks → Build → bootJar**를 먼저 실행해서 실행 가능한 JAR 파일부터 만들어줘야 한다. (Dockerfile이 이 JAR 파일을 이미지 안에 복사해서 넣는 방식이기 때문에, JAR이 먼저 준비돼 있어야 한다.)

### 컨테이너 실행 & 포트 매핑
```bash
docker run -p {외부 포트번호}:{컨테이너 내부 포트번호} {이미지 이름}:{이미지 버전}

# 예시
docker run -p 60080:8080 -d catohgiraffers/springbootdocker:latest
```
- `-p 60080:8080`은 **"내 컴퓨터(외부)의 60080번 포트로 들어온 요청을, 컨테이너 안의 8080번 포트로 연결해줘"**라는 뜻이다. 앞이 외부(호스트), 뒤가 컨테이너 내부라는 순서를 기억하면 된다.
- `-d`는 어제 배운 것처럼 백그라운드 실행 옵션이다.

### docker-compose란?
여러 컨테이너(예: 백엔드 서버 + DB + 캐시 서버 등)를 매번 `docker run` 명령어로 하나씩 따로 실행하면 번거롭고 설정을 맞추기도 어렵다. **docker-compose**는 이런 여러 컨테이너의 설정(이미지, 포트, 환경변수, 볼륨 등)을 **하나의 yml 파일에 모아 적어두고, 명령어 한 번(`docker compose up`)으로 한꺼번에 실행/관리**할 수 있게 해주는 도구다.

## 4. 클라우드 서버 개요

### 클라우드 서버란?
**클라우드 서버(cloud server)**는 인터넷 상의 가상화된 서버로, 필요할 때마다 접근해서 사용할 수 있는 서버다. "클라우드"라는 용어는 에릭 슈미트(전 구글 CEO)가 처음 정의했고, 제프 베조스가 처음으로 클라우드 서비스를 만들었다고 한다.

인터넷 통신망에만 접근할 수 있으면 컴퓨터 자원(CPU, 메모리, 디스크 등)을 원하는 대로 가져다 쓸 수 있어서, **"소유"에서 "대여/사용"으로 패러다임이 바뀌었다**는 게 핵심이다. 기존 물리 서버와 기능(처리 성능, 스토리지, 애플리케이션 제공)은 동일하지만, 필요한 성능에 따라 유동적으로 규모를 선택할 수 있다는 게 물리 서버 대비 장점이다.

### 하이퍼바이저(Hypervisor)와 클라우드 서비스 모델
클라우드 서버는 **가상화**로 구현된다. **하이퍼바이저**라는 관리 소프트웨어가 물리 서버에 설치돼서 자원을 결합·추상화하고, 그 위에 가상의 서버(VM)를 여러 개 만들어낸다.

- **Type1 (베어메탈 하이퍼바이저)**: 하드웨어 위에 직접 설치. 예: VMware ESXi, Microsoft Hyper-V, Xen
- **Type2 (호스트 하이퍼바이저)**: 호스트 운영체제 위에서 실행. 예: VMware Workstation, Oracle VirtualBox (어제 실습 때 비교했던 VirtualBox가 여기 해당한다)

클라우드는 제공 범위에 따라 아래 3가지 모델로 구분된다.

| 모델 | 제공 범위 | 예시 |
|---|---|---|
| **IaaS** (Infrastructure as a Service) | 가상 서버, 호스팅, 스토리지, 가상 네트워크 등 인프라 자체를 서비스로 제공. 사용자는 물리 자원 관리를 직접 안 해도 되고, 사용한 만큼만 비용 지불 | AWS, Microsoft Azure |
| **PaaS** (Platform as a Service) | 미들웨어, 데이터베이스 관리, 애널리틱스, OS 등을 제공. 하드웨어·OS·미들웨어 관리는 제공자가 하고, 사용자는 애플리케이션 실행에만 집중 | (AWS Elastic Beanstalk가 대표적인 PaaS 성격의 서비스) |
| **SaaS** (Software as a Service) | 소프트웨어/애플리케이션 기능 자체를 제공 | 네이버 클라우드, 웹 메일 등 |

### 클라우드 서버의 장단점
- **경제성**: 자체 인프라 구매·관리보다 비용 부담이 적고, 사용한 리소스만큼만 비용을 낸다.
- **편의성**: 서버 구축이 몇 분 안에 끝나고, 자원 관리도 클라우드 회사가 담당해준다.
- **확장성**: 필요에 따라 서버 저장소·자원을 빠르게 확장/축소할 수 있다.
- **안정성**: 물리 서버와 동일한 성능을 제공하고, 공유 환경에서 여러 서버가 돌기 때문에 한 서버에 문제가 생겨도 빠르게 복구/지속이 가능하다.

### 클라우드 서버를 도입하는 이유
새 제품/서비스 출시 시 서버 리소스를 적시에 확보할 수 있고, 이론상 무한 확장이 가능하며, 초기 투자 비용이 물리 서버 구축 방식보다 훨씬 적다는 점이 핵심이다.

## 6. AWS 주요 서비스

| 서비스 | 역할 |
|---|---|
| **EC2** (Elastic Compute Cloud) | AWS의 가장 기본적인 인프라, 네트워크 망에서 가상 서버(=인스턴스)를 제공한다. 인터페이스를 통해 유동적인 스펙의 서버를 빠르게 구축할 수 있다. |
| **S3** (Simple Storage Service) | 사진·비디오·문서 같은 파일을 저장하는 오브젝트 스토리지. "버킷" 단위로 운용되고, 다른 유저의 접근 권한도 제어할 수 있다. 무제한 확장성과 높은 가용성·내구성을 보장하고, 단일 파일은 최대 5TB까지 업로드 가능하다. |
| **VPC** (Virtual Private Cloud) | 계정별로 격리된 네트워크 환경을 구성하는 서비스. 서브넷, Route Table, ACL, 보안 그룹 등으로 논리적인 네트워크 분할이 가능하고, 계정 안/간 격리된 네트워크를 연결하는 옵션도 제공한다. AWS 리소스 간 허용 범위를 최소화하고 그룹별 네트워크 구성을 쉽게 하기 위해 사용한다. |
| **IAM** (Identity and Access Management) | 권한 관리 서비스. AWS 계정을 만들면 기본으로 Root 계정이 생기는데, 이 계정은 **모든 권한을 가지고 있어 보안상 위험**하다. IAM으로 사용자 계정·그룹을 따로 만들어서 필요한 권한만 부여하는 것이 권장된다 — 즉, 평소 작업은 Root가 아니라 IAM으로 만든 계정으로 하는 게 안전하다. |
| **Route 53** | 도메인 관리/설정(DNS) 서비스. EC2 인스턴스, Elastic 로드밸런서, S3 저장소 등에 연결해서 쓰고, 기존에 가진 도메인을 연결하거나 Route53에서 직접 도메인을 구입할 수도 있다. |
| **ECS** (Elastic Container Service) | AWS의 매니지드 컨테이너 오케스트레이션 서비스. EC2에 클러스터를 만들고 EC2 인스턴스를 등록한 뒤, 서비스와 Task 단위로 도커 컨테이너를 클러스터 위에 스케줄한다. |
| **EKS** (Elastic Kubernetes Service) | 관리형 쿠버네티스 서비스. 원래 직접 구성해야 하는 쿠버네티스 마스터 노드를 AWS가 대신 관리해줘서 빠르게 쿠버네티스를 쓸 수 있다. EKS 클러스터 생성과 노드 그룹 생성이 필요하다. |
| **SQS** (Simple Queue Service) | AWS의 첫 번째 서비스이기도 한 관리형 메시지 큐. 애플리케이션 간 메시지를 전달하는 대기열이며, 메시지가 전달된 순서대로 정확히 처리하는 FIFO 대기열을 지원한다. |
| **Lambda** | 서버리스 컴퓨팅 서비스. 애플리케이션 실행용 별도 서버 없이 코드를 바로 실행해준다. 고정 비용 없이 사용한 시간만큼만 과금되는데, EC2가 초 단위 과금인 반면 Lambda는 1ms 단위로 계산해서 더 정교하게 비용이 발생한다. |
| **Elastic Beanstalk** | 코드(WAR/JAR 등)만 업로드하면 서버 생성, 배포, 로드밸런싱, 오토스케일링, 상태 모니터링까지 **AWS가 자동으로 관리**해주는 배포 서비스다. EC2를 직접 하나하나 설정하는 IaaS 방식과 달리, PaaS에 가깝게 "인프라 신경 안 쓰고 배포만" 할 수 있게 해주는 게 핵심이다. |

## 7. AWS 프리티어

문서상 정의는 다음과 같다: **AWS 프리티어**는 처음 가입 후 1년 동안 서비스별로 정해진 한도 내에서 무료로 사용할 수 있는 제도이고, 모든 서비스가 무료는 아니기 때문에 불필요한 과금이 되지 않도록 항상 주의해야 한다.

> 참고로 어제 수업에서는 "요즘은 1년 무료 대신 가입 시 200달러 크레딧을 주고 그걸 다 쓰면 종료되는 방식으로 바뀌었다"는 이야기도 나왔었다. 문서상 설명(1년 한도 내 무료)과 최근 정책(크레딧 소진형)이 다르게 느껴질 수 있는데, AWS가 최근에 프리티어 정책을 개편한 것으로 보인다 — 실제로 계정을 만들 때는 가입 시점 기준 최신 정책을 AWS 콘솔에서 다시 한번 확인하는 게 안전하다.

## 8. 원격 접속 도구 — MobaXterm

어제 SSH 접속 도구로 이름만 언급됐던 **MobaXterm**을 조금 더 짚어보면, Windows에서 리눅스 서버(EC2 인스턴스 등)에 편하게 접속하기 위한 프로그램이다. SSH 터미널 접속뿐 아니라, 파일을 끌어다 옮길 수 있는 SFTP 파일 탐색기, 여러 원격 접속 세션 관리, X11 포워딩(리눅스 GUI 화면 띄우기) 같은 기능을 한 프로그램 안에 묶어서 제공한다. Mac/Linux는 기본 터미널로 바로 SSH 접속이 되지만, Windows는 이런 통합 도구를 쓰면 서버 접속과 파일 관리를 훨씬 편하게 할 수 있다.

- terminus, putty도 접속 툴인데, terminus는 UI가 예쁘고 putty는 오래됨
