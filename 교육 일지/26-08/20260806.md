## 1. 사유별 점수 획득 현황 API

### 목적
점수 변동 사유(레시피 등록, 만료 방어 성공, 만료 방치 등)별로 **발생 횟수**와 **합계 점수**를 집계해서 보여준다.

### 핵심 구현

**Repository (`ScoreAnalysisRepository`)** — JPQL의 `new` 생성자 표현식을 사용해, 쿼리 결과를 바로 DTO로 매핑했다.

```java
@Query("""
        SELECT new com.naengpa...ScoreByReasonResponse(
                    CAST(sh.scoreReason AS string), COUNT(sh), SUM(sh.scoreDelta)
        )
        FROM ScoreHistory sh
        WHERE sh.memberId = :memberId
        AND sh.createdAt >= :startOfMonth
        GROUP BY sh.scoreReason
        """)
List<ScoreByReasonResponse> findScoreSummaryByReason(
        @Param("memberId") Long memberId,
        @Param("startOfMonth") LocalDateTime startOfMonth);
```

### 배운 것 / 트러블슈팅

- **JPQL 생성자 표현식에서 Enum → String 변환**: `ScoreReason`은 Enum 타입이라, DTO의 `String` 필드에 바로 못 들어간다. `CAST(sh.scoreReason AS string)`으로 명시적으로 형변환해야 함.
- **집계 함수의 반환 타입 규칙**: `COUNT()`, `SUM()`은 원본 필드가 `Integer`여도 항상 `Long`을 반환한다. DTO 필드를 원시타입(`long`, `int`)이 아니라 래퍼타입(`Long`, `Integer`)으로 맞춰야 JPQL 생성자 매칭이 성공한다. 이 부분에서 타입 불일치로 인한 컴파일 에러를 겪고 원인을 찾아 해결했다.
- 이 프로젝트에서는 별도의 Projection 인터페이스보다, **팀 기존 코드(`ExpiredProductCategoryResponse`)와 동일한 "JPQL new 생성자 표현식" 패턴**을 따르는 것이 컨벤션에 맞다고 판단해 그대로 적용했다.

## 2. 이번 달 점수 변동 요약 API

### 목적
이번 달 1일부터 오늘까지의 **총 획득 점수**, **총 감점**, **순변동**을 계산해서 보여준다.

### 핵심 구현

```java
@Query("""
        SELECT new com.naengpa...ScoreSummaryResponse(
                    SUM(CASE WHEN sh.scoreDelta > 0 THEN sh.scoreDelta ELSE 0 END),
                    SUM(CASE WHEN sh.scoreDelta < 0 THEN sh.scoreDelta ELSE 0 END),
                    SUM(sh.scoreDelta)
        )
        FROM ScoreHistory sh
        WHERE sh.memberId = :memberId
        AND sh.createdAt >= :startOfMonth
        """)
ScoreSummaryResponse findMonthlySummary(
        @Param("memberId") Long memberId,
        @Param("startOfMonth") LocalDateTime startOfMonth);
```

**`CASE WHEN`**을 이용해 양수/음수를 구분해서 각각 합산했다. (자바의 삼항 연산자와 동일한 역할을 SQL에서 수행)

### 설계 결정 — 조회 기간

- 기존 팀 기능들(만료 통계: 최근 7일, 관리자 대시보드: 최근 7일/30일/전체 선택)과 기간 방식이 다르지만, **"점수 분석"은 월 단위 리포트 성격**(카드 명세서, 은행 거래 요약과 유사)이 자연스럽다고 판단해 **이번 달(1일~오늘) 기준**으로 확정했다.
- 같은 프로젝트 안에서도 기능 목적에 따라 조회 기간 방식이 다른 것은 자연스러운 설계이며, 오히려 "왜 이렇게 설계했는가"를 설명할 수 있는 근거가 된다는 결론에 도달했다.
- **사유별 현황 API에도 동일하게 "이번 달" 필터를 추가**했다. 이유: 다음에 만들 "이번 달 최대 영향 사유" API가 이 API의 결과를 그대로 재사용할 예정인데, 사유별 현황이 전체 기간이면 "이번 달 최대 영향 사유"라는 이름과 실제 내용이 맞지 않게 되는 논리적 모순을 발견해 사전에 수정했다.

### API URL 설계

- 처음엔 `/analysis/monthly-summary`로 설계했으나, "이번 달"이라는 기준이 향후 바뀔 가능성을 고려해 `/analysis/summary`로 URL을 일반화했다. 구현 로직(월 단위 집계)과 API 계약(URL)을 분리해, 나중에 집계 기준만 바뀌어도 URL을 유지할 수 있도록 설계했다.

## 오늘 배운 점 정리

1. JPQL의 `new` 생성자 표현식을 사용할 때는 **DTO 필드 타입을 집계 함수의 실제 반환 타입(Long, 래퍼타입)과 정확히 맞춰야 한다.**
2. Enum 타입 필드를 문자열로 받으려면 **`CAST(... AS string)`으로 명시적 형변환**이 필요하다.
3. 하나의 프로젝트 안에서도 **각 기능의 목적에 맞게 조회 기간 정책을 다르게 설계**하는 것이 자연스러우며, 그 이유를 설명할 수 있으면 오히려 설계 근거가 된다.
4. API를 여러 개로 나눌 때, 한 API의 결과를 다른 API가 재사용하는 구조라면 **두 API의 "이름이 암시하는 의미"가 서로 어긋나지 않는지** 먼저 점검해야 한다. (오늘 사유별 현황 API에 뒤늦게 기간 필터를 추가하게 된 이유)
