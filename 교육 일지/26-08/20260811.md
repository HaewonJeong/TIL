## 1. 퀴즈 생성 라우터 구현

### 목적
Spring 백엔드가 호출하면, 주어진 재료(ingredient)를 기반으로 O/X 퀴즈 하나를 생성해서 JSON으로 반환하는 API를 FastAPI에 추가한다.

### 핵심 구현

```python
import os
from fastapi import APIRouter
from openai import OpenAI
import json

router = APIRouter(prefix="/quiz", tags=["quiz"])
client = OpenAI()
MODEL = os.getenv("OPENAI_MODEL", "gpt-4.1-mini")

@router.get("/generate")
def generate_quiz(ingredient: str):
    prompt = f"""
    반드시 "{ingredient}"에 대한 O/X 퀴즈를 만들어줘. 다른 재료는 절대 사용하지 마.

    "{ingredient}"의 보관, 소비, 신선도 유지와 관련된 O/X 퀴즈를 하나 만들어줘.

    조건: 
    - 반드시 "{ingredient}"에 관한 내용이어야 해. 다른 재료를 언급하면 안 돼.
    - 일반적으로 널리 알려진 식품 안전/보관 상식만 사용해.
    - 불확실한 정보는 만들지 마.
    - 너무 뻔하지 않게, 헷갈릴 만한 내용으로 만들어줘.

    아래 JSON 형식으로만 답해:
    {{
        "statement": "O/X로 답할 수 있는 문장",
        "answer": true 또는 false,
        "explanation": "정답 이유 한 줄",
        "confidence": "high 또는 medium 또는 low"
    }}
    """

    response = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": prompt}]
    )

    result = json.loads(response.choices[0].message.content)
    return result
```

`main.py`에 라우터 등록:

```python
from app.api.quiz import router as quiz_router
app.include_router(quiz_router)
```

기존에 팀원들이 만들어둔 `health`, `shopping_recommendations`, `inquiry_chat` 라우터와 동일한 패턴으로 추가하여, 이미 존재하는 FastAPI 서버(Agent 프로젝트) 구조를 그대로 따랐다.

## 2. 트러블슈팅

### (1) `openai` 패키지 버전 문제

**증상**: `ImportError: cannot import name 'OpenAI' from 'openai'`

**원인**: 설치된 `openai` 패키지가 옛날 버전(0.28 이하)이라, 최신 문법(`from openai import OpenAI`)을 지원하지 않았다.

**해결**: `pip install --upgrade openai`로 최신 버전 설치.

### (2) API 키 미설정

**증상**: `openai.OpenAIError: Missing credentials. ... set the OPENAI_API_KEY ...`

**원인**: `.env.example`은 값이 비어있는 예시 파일이고, 실제 값이 담긴 `.env`가 없었거나 키가 비어 있었다.

**해결**: `.env` 파일에 실제 `OPENAI_API_KEY` 값을 채워 넣음.

### (3) 프롬프트 정확도 문제

**증상**: `ingredient=아몬드우유`로 요청했는데, 응답이 "토마토"에 대한 퀴즈로 나옴.

**원인**: 프롬프트가 짧고 "반드시 이 재료로만"이라는 지시가 약해서, LLM이 가끔 지시를 무시하고 다른 재료로 답함.

**해결**: 프롬프트 맨 앞과 조건 목록 양쪽에 "반드시 ~에 대한 내용, 다른 재료 언급 금지"를 명시적으로 두 번 강조. 이후 여러 재료로 반복 테스트해 정상 동작 확인.

### (4) Git 브랜치 관리 (main 오염)

**증상**: `git pull origin dev`를 `main` 브랜치에 있는 상태로 실행해, 로컬 `main`이 `dev` 내용과 동일해짐(`HEAD -> main, origin/dev`).

**원인**: 브랜치 전환(`checkout dev`) 없이 다른 브랜치의 내용을 바로 pull 받음.

**해결**: `git reset --hard origin/main`으로 로컬 main을 원격 상태로 되돌린 뒤, `git checkout dev`로 정상적으로 전환. (push 하기 전에 발견해 원격 저장소에는 영향 없었음)

## 3. 설계 관련 결정 사항

- FastAPI 서버는 팀원이 이미 구축해둔 공용 Agent 서버(`NaengpaMaster Agent`)에 라우터로 추가하는 방식을 택함. 별도 서버를 새로 구축하지 않아 개발 속도와 인프라 복잡도를 줄임.
- 공용 서버에 코드를 추가하는 작업이므로, 작업 전 팀 채널에 미리 공유하고 진행함.
- 모델명은 하드코딩하지 않고 환경변수(`OPENAI_MODEL`)로 관리, 기본값만 코드에 명시하여 배포 환경별로 유연하게 전환 가능하도록 설계.

## 4. PR 관련

- 최초 PR에 오타(`entitiy` → `entity` 등)를 뒤늦게 발견했으나, 이미 승인/머지된 PR은 직접 수정하지 않고 별도 브랜치를 만들어 `git cherry-pick`으로 해당 커밋만 옮겨 새 PR로 분리 제출함.
- 다른 브랜치의 특정 커밋만 골라 가져오는 `cherry-pick` 사용법을 실제로 익힘.

## 오늘(당시 기준) 배운 점 정리

1. LLM에게 특정 조건(재료 고정)을 지키게 하려면, 지시를 한 번이 아니라 앞뒤로 반복 강조하는 것이 실제로 정확도에 영향을 준다.
2. `git pull`은 반드시 목표 브랜치로 전환한 뒤 실행해야 하며, 그렇지 않으면 의도치 않게 현재 브랜치가 오염될 수 있다. 다행히 push 전에 발견하면 `reset --hard origin/브랜치명`으로 안전하게 복구 가능하다.
3. 이미 승인/머지된 PR에 대한 추가 수정은, 해당 브랜치를 다시 여는 대신 새 브랜치 + `cherry-pick`으로 독립적인 PR로 분리하는 것이 리뷰 흐름을 깔끔하게 유지하는 방법이다.
4. 외부 서비스(FastAPI)에 새 기능을 추가할 때도, 이미 존재하는 프로젝트의 구조와 패턴(라우터 등록 방식 등)을 그대로 따르는 것이 협업 관점에서 안전하다.
