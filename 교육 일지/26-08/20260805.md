## 오늘 나온 핵심 개념 (한눈에 보기)

| 개념 | 한 줄 정의 |
|---|---|
| **정적 사이트(Static Export)** | 서버 없이 HTML/CSS/JS 파일만으로 동작하는 사이트. Next.js를 `output: "export"`로 빌드하면 `out/` 폴더에 생성됨 |
| **S3 정적 웹 호스팅** | S3 버킷을 "파일 저장소"가 아니라 "웹사이트 서버"처럼 쓰는 기능. 빌드된 정적 파일을 올려두면 그 자체로 웹사이트가 됨 |
| **Elastic Beanstalk (EB)** | 코드/이미지만 올리면 서버 생성부터 배포까지 AWS가 자동 관리해주는 PaaS형 배포 서비스 (어제 배운 개념의 실전 버전) |
| **Single Instance 환경** | EB 배포 방식 중 로드밸런서(ALB) 없이 EC2 인스턴스 1대로만 운영하는 가장 단순한 구성 |
| **DockerHub** | 만든 Docker 이미지를 올려두는 공개 이미지 저장소. EB가 여기서 이미지를 받아와 실행함 |
| **Dockerrun.aws.json** | "EB야, 이 DockerHub 이미지를 이 포트로 실행해줘"라고 알려주는 EB 전용 설정 파일 |
| **GitHub Actions** | 코드를 push하면 자동으로 테스트·빌드·배포를 실행해주는 CI/CD 도구 |
| **GitHub Secrets** | API 키, 비밀번호처럼 코드에 직접 적으면 안 되는 값을 GitHub 저장소에 암호화해서 저장해두는 곳 |
| **IAM 최소 권한 정책** | 계정에 필요한 작업(S3, EB 등)만 딱 허용하고 나머지는 막아두는 보안 원칙 |
| **base64 인코딩** | `application-dev.yml`처럼 여러 줄의 설정 파일을 한 줄의 문자열로 바꿔서 GitHub Secrets에 안전하게 저장하기 위한 방법 |
| **Health Check (`/actuator/health/liveness`)** | 배포된 애플리케이션이 "죽지 않고 살아있는지"만 확인하는 전용 확인 경로 (DB 상태와는 무관) |

## 1. 전체 아키텍처

```
[User Browser]
  ├── React/Next.js 정적 파일 → S3 Website (HTTP)
  └── Spring Boot API → Elastic Beanstalk Single instance → DockerHub Image
```

- **프론트엔드(React/Next.js)**: Docker 없이 그냥 정적 파일로 빌드해서 S3에 업로드한다.
- **백엔드(Spring Boot)**: Docker 이미지로 빌드 → DockerHub에 업로드 → Elastic Beanstalk이 그 이미지를 가져와 실행한다.
- 즉, 프론트와 백엔드가 완전히 분리된 배포 방식이고, 브라우저가 S3에서 화면을 받아온 뒤 API 요청만 EB 서버로 따로 보내는 구조다.

## 3. 배포 준비 체크리스트 흐름

오늘 실습은 아래 순서로 진행됐다.

1. **IAM 사용자 생성** (`github-actions-user`) — S3/Elastic Beanstalk 작업만 허용하는 최소 권한 정책 부여. DockerHub를 쓰기 때문에 `AmazonEC2ContainerRegistryFullAccess`(ECR 권한)는 필요 없었다. Access Key를 발급해서 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`로 GitHub Secrets에 등록. (참고로 운영 환경에서는 Access Key보다 **GitHub OIDC 임시 자격증명** 방식이 더 권장된다고 한다.)
2. **S3 버킷 생성** — EB 배포용 ZIP을 올릴 버킷(`my-eb-deploy-bucket`)과, React 정적 파일을 올려 퍼블릭으로 읽게 할 버킷을 준비. 버킷 정책에 `s3:GetObject`를 `Principal: "*"`로 허용해서 누구나 파일을 읽을 수 있게 설정한다.
3. **DockerHub 세팅** — 계정 생성 후 공개 리포지토리 준비, `DOCKER_USERNAME`/`DOCKER_PASSWORD`를 Secrets에 등록.
4. **Elastic Beanstalk 애플리케이션 생성** — 플랫폼은 `Docker running on 64bit Amazon Linux 2023`, 환경 유형은 `Single instance`(로드밸런서 없음), 포트는 8080. 서비스 액세스/네트워킹/트래픽/모니터링은 기본값으로 설정.
5. **GitHub Secrets에 설정 파일 등록** — `application-dev.yml`은 깃허브에 그대로 커밋하면 DB 비밀번호나 JWT 키가 노출되니까, 파일 전체를 base64로 인코딩해서 `APPLICATION_DEV_YML`이라는 Secret 하나로 저장한다.
6. **보안 그룹 확인** — Single instance 환경에서는 EB가 만든 프록시를 통해 접근하므로, 실습에 필요한 포트만 열어두고 수업이 끝나면 환경을 종료해서 비용이 새지 않게 한다.
7. **배포 후 헬스체크** — `http://EB환경주소/actuator/health/liveness`에 요청해서 `{"status":"UP"}`(HTTP 200)이 나오는지 확인한다. 이 경로는 DB 연결과 무관하게 "애플리케이션 프로세스 자체가 살아있는지"만 보는 것이 포인트다.

## 4. CI/CD 파이프라인

### React → S3 (GitHub Actions)
- `next.config.mjs`의 `output: "export"` 설정 덕분에 `npm run build`만 하면 정적 파일이 `out/` 폴더에 생긴다 — **S3 배포에서는 별도 Dockerfile이 필요 없다.**
- Actions 흐름: 체크아웃 → Node 20 설치 → `npm ci` → lint → `npm run build`(이때 `NEXT_PUBLIC_API_BASE_URL` 같은 값을 build-time 환경변수로 주입) → AWS 자격증명 설정 → `aws s3 sync out/ "s3://$S3_BUCKET_NAME" --delete`로 S3에 통째로 동기화(기존 파일 중 없어진 건 `--delete`로 같이 정리).

### Spring Boot → DockerHub → Elastic Beanstalk (GitHub Actions)
- 흐름: 체크아웃 → Java 21 설치 → `application-dev.yml`을 Secret에서 base64 디코딩해서 실제 파일로 복원 → `./gradlew clean build`로 JAR 빌드 → DockerHub 로그인 → 이미지 빌드·푸시(태그는 커밋 SHA로 매번 새로 발급) → **`Dockerrun.aws.json`** 생성(어떤 이미지를, 몇 번 포트로 실행할지 EB에게 알려주는 파일) → 이 파일을 zip으로 묶어 S3에 업로드 → `aws elasticbeanstalk create-application-version`으로 새 배포 버전 등록 → `aws elasticbeanstalk update-environment`로 실제 환경에 그 버전을 적용(무중단 방식으로 새 이미지로 교체).
- 버전 라벨을 `v${{ github.run_number }}-${{ github.run_attempt }}`처럼 매번 다르게 만들어서, EB가 "이건 새 배포다"라고 인식하게 만드는 부분이 실무적으로 중요한 디테일이었다.

### GitHub Secrets 전체 목록 (오늘 등록한 것)
| 키 | 설명 |
|---|---|
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | IAM 사용자 키 |
| `AWS_REGION` | 예: `ap-northeast-2` |
| `APPLICATION_DEV_YML` | base64 인코딩된 Spring 설정 파일 |
| `S3_BUCKET_NAME` | React 배포용 버킷명 |
| `EB_APP_NAME` / `EB_ENV_NAME` | Spring Boot용 EB 애플리케이션/환경 이름 |
| `DOCKER_USERNAME` / `DOCKER_PASSWORD` | DockerHub 계정 정보 |

## 5. 프론트엔드 쪽 이미지 URL 처리 (`resolveImageUrl`)

로컬에서는 이미지 주소가 `http://localhost:8080/...`이지만 배포 후에는 실제 EB 주소로 바뀌어야 하므로, 상대경로/절대경로를 구분해서 자동으로 백엔드 주소를 붙여주는 유틸 함수를 적용했다.

```jsx
const API_BASE_URL = process.env.NEXT_PUBLIC_API_BASE_URL || "http://localhost:8080";

export function resolveImageUrl(imageUrl) {
  if (!imageUrl) return "";
  // 이미 완성된 절대 URL이면 그대로 사용
  if (/^(https?:)?\/\//i.test(imageUrl) || /^(data|blob):/i.test(imageUrl)) {
    return imageUrl;
  }
  // 상대경로일 때만 백엔드 주소를 붙임
  return `${API_BASE_URL.replace(/\/$/, "")}/${imageUrl.replace(/^\/+/, "")}`;
}
```
기존에는 이미지 태그마다 `API_BASE_URL + productImageUrl`을 직접 이어붙였는데, 이 함수로 감싸면 이미 완성된 URL(예: 외부 이미지 링크)이 들어와도 중복으로 주소가 붙는 실수를 막을 수 있다.

- S3 버킷 생성, Elastic Beanstalk 애플리케이션/인스턴스 생성, GitHub Actions Secret 값 등록까지 직접 진행했다.
- 프론트엔드/백엔드 코드는 강사님이 주신 파일을 그대로 올려서 배포했다.
- S3 버킷의 `index.html`을 열어 프론트엔드 화면까지는 확인했지만, **백엔드(EB)와의 연결은 아직 안 되는 상태**로 마무리됐다.

### 다음에 확인해볼 만한 부분 (연결 안 될 때 체크리스트)
연결이 안 되는 원인은 보통 아래 중 하나인 경우가 많으니, 다음 시간에 위에서부터 순서대로 확인해보면 좋을 것 같다.

1. **`NEXT_PUBLIC_API_BASE_URL` 값 확인** — Next.js의 `NEXT_PUBLIC_*` 환경변수는 **빌드 시점에 정적 파일 안에 박제**된다. GitHub Secrets에 이 값이 EB의 실제 환경 주소(`http://...elasticbeanstalk.com`)로 정확히 등록돼 있는지, 그리고 그 값으로 다시 빌드해서 S3에 올렸는지 확인이 필요하다.
2. **EB 헬스체크 통과 여부** — `http://EB환경주소/actuator/health/liveness`에 직접 접속해서 `{"status":"UP"}`이 뜨는지 먼저 확인 (여기서 안 뜨면 프론트 문제가 아니라 백엔드/EB 배포 자체의 문제).
3. **보안 그룹 포트 개방 여부** — EB 인스턴스의 보안 그룹에서 8080(또는 EB가 프록시하는 80) 포트가 실제로 열려 있는지 확인.
4. **CORS 설정** — S3(정적 사이트) 도메인에서 EB 서버로 요청을 보낼 때, Spring Boot 쪽에 해당 S3 도메인을 허용하는 CORS 설정이 있는지 확인.
5. **HTTP/HTTPS 혼합 콘텐츠 여부** — S3 정적 호스팅과 EB가 둘 다 HTTP라 이 부분은 크게 문제 없을 가능성이 높지만, 혹시 브라우저 콘솔에 mixed content 관련 에러가 있는지도 한 번 확인해보면 좋다.
6. **`application-dev.yml`이 제대로 복원됐는지** — GitHub Actions 로그에서 base64 디코딩 단계가 에러 없이 지나갔는지, DB 접속 정보(`sql.macacolabs.site:3300`)가 실제로 맞는지도 확인 대상이다.
